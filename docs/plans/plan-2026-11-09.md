# Plan — 2026-11-09

## Vision

One workspace, no uploads, verified output.

A free PDF tool for people without an Acrobat license. Drop in any mix of PDFs
and images; every page appears in one grid. Arrange, rotate, delete, sign and
type on pages, then export once. Files never leave the device, and the site
refuses to hand over an output it could not verify.

The gap this fills: existing tools (iLovePDF, Smallpdf, BentoPDF, Stirling-PDF)
are one tool per page, so a merge-reorder-sign job means three round trips.
Research: `docs/research/2026-11-09-summary.md`.

## Principles

1. **Avoid, don't fail.** A feature ships only if it is near-100% reliable. Anything
   lossy or heuristic (PDF to Word, text editing, client OCR, PDF/A) is out.
2. **Verified output.** Every export passes `qpdf --check`, a page-count and
   page-size comparison against the plan, and a re-open in PDF.js before the
   download button appears. A failure shows what failed; no file is offered.
3. **Local, provably.** Phase 1 makes no network request after load. A
   Content-Security-Policy with `connect-src 'self'` enforces it. No analytics
   script, no third-party fonts, no CDN.
4. **Non-destructive.** The user's edits are a list of page references and
   stamps (`ExportPlan`). Originals are never modified; undo is free.
5. **Phone is a first-class layout,** not a shrunken desktop.
6. **Fast.** Static site. The shell loads without any PDF engine; engines load
   on first file. Budget: under 150 KB of JS before the first file is opened.

## Phases

| Phase | Scope |
|---|---|
| 1 | Merge, reorder, rotate, delete, duplicate, insert blank or other pages, extract/split, images to PDF, add or remove a known password, lossless compress, strip metadata, sign and type-on-page (signature, initials, text, date, check/cross marks), installable PWA, offline |
| 2 | True redaction with verification (MuPDF, lazy-loaded), real AcroForm fields, compress to a target size, page numbers and Bates stamps, highlight |
| 3 | Opt-in server jobs on a separate origin: OCR, Office to PDF |
| Never | PDF to Word, text editing, certificate signatures, send-for-signature, PDF/A, XFA forms |

## Architecture

SvelteKit 3 + Svelte 5 runes + TypeScript, `adapter-static`, SPA (`ssr = false`),
deployed as a Cloudflare Worker with static assets (`wrangler.jsonc`). Contracts live in `src/lib/core/types.ts`.

```
files ──► Engine.openPdf / openImage ──► Source (normalized PDF bytes)
                                            │
            DocStore: Source[] + PageRef[] + Asset[] + undo history
                 │                          │
        Renderer (PDF.js)            Engine.exportPlan
        thumbnails, page view        qpdf assemble ► pdf-lib stamps ► qpdf finalize ► verify
```

- **Engine** (`src/lib/engine/`) runs in a Web Worker.
  - Intake: `qpdf` decrypts and rewrites every input, which also repairs damaged
    cross-reference tables. If qpdf reports errors the file is rejected as unreadable;
    warnings become `Source.notes`.
  - Assemble: one `qpdf --empty --pages … --` call builds the page order, with
    `--rotate` for user rotation.
  - Stamps: only when the plan has stamps, `@cantoo/pdf-lib` opens the assembled
    file and draws images, text (embedded, subset font) and vector marks, honoring
    page rotation and CropBox.
  - Finalize: qpdf applies object streams and stream recompression (`compress`),
    AES-256 encryption (`password`), and metadata removal.
  - Verify: see principle 2.
- **Renderer** (`src/lib/render/`) wraps PDF.js: worker-based, lazy, cancelable,
  bitmap cache with a memory cap, pixel cap for iOS (16.7 MP per canvas).
- **DocStore** (`src/lib/doc/`) is framework-free TypeScript: state, commands,
  undo/redo. Svelte components subscribe through a thin runes adapter.
- **Workspace** (`src/lib/workspace/`) is the page grid and its actions.
- **Editor** (`src/lib/editor/`) is the single-page view for placing stamps.
- **UI kit** (`src/lib/ui/`) holds tokens and shared components. See `DESIGN.md`.

## Phase 2 design (2026-11-10)

Contracts for all of this are in `src/lib/core/types.ts`. MuPDF.js (`mupdf`, AGPL)
is the second engine: loaded by dynamic `import()` in the engine worker only when
a plan needs it (form fields, redaction, target size). It is never in the entry bundle.

Export pipeline, in order. Stages in brackets run only when the plan asks for them:

```
qpdf assemble ► [forms: set values, flatten] ► [redact] ► [stamps + numbering]
            ► [shrink images ► ] qpdf finalize ► verify
```

| Feature | How | Check that must pass (else no file) | Left out on purpose |
|---|---|---|---|
| Highlight | `highlight` stamp drawn with Multiply blend by pdf-lib: a box (slightly rounded rectangle), or with `pen` (2026-11-10) a freehand stroke, `PenStroke` = points in stamp space plus a width as a fraction of page height, drawn as one stroked path with round caps and joins; `box` then covers the stroke and moves with its points. The editor's Pen (default) simplifies strokes (RDP) and stores nearly straight ones as a two-point line snapped to level/upright within 4° | usual checks; pen points must lie inside `box` | snapping to text lines (heuristic); resizing a pen stroke |
| Page numbers, Bates | `ExportOptions.numbering`; text in the stamp font, 0.5 in from the edge, upright on rotated pages | `numbering`: each label is read back from its page | per-page overrides, custom fonts |
| Redaction | `redact` stamp; MuPDF redaction annotations applied (text glyphs, image pixels, line art, links and annotations under the box). Forms are flattened first and metadata is stripped | `redaction`: two engines (MuPDF, PDF.js) find no text under any box, the box renders solid black; checked right after the stage and again on the final file (own stamps over a box are allowed) | search-and-redact, whole-page raster fallback |
| Form filling | `Engine.formFields` lists text, checkbox, radio and choice fields; answers live per source in `FormValues`; MuPDF writes values and appearances; optional flatten | `forms`: every answer reads back from the final file (or, flattened, no fields remain and text answers are on the page) | XFA, signature fields, fields computed by form scripts (shown read-only), rich text, comb layout fidelity beyond MuPDF's |
| Target size | `ExportOptions.targetBytes`; ladder of image resolution caps and JPEG quality, stops at the first step that fits; only plain 8-bit grey/RGB images are re-encoded | `visual`: each page rendered before and after must match within a tolerance; `target-size` | re-encoding 1-bit scans, CMYK, masked or indexed images; font subsetting |

Rules that follow from "avoid, don't fail":

- A redaction box that cannot be verified refuses the export; there is no "cover only" fallback.
- If the size target cannot be reached, the smallest verified file is offered with the real size.
- A source page duplicated in the grid shares its form answers with its copies (answers belong to the source).
- Form answers in thumbnails and the page view are a PDF.js preview; the exported appearance is MuPDF's.

Streams and paths are as in the ownership table. Engine work is split by module
(`mupdf.ts` loader, `forms.ts`, `redact.ts`, `shrink.ts`, `numbering.ts`), each with
its own test file, so streams do not edit the same code.

- Survey fix round 1 (intake/assemble/forms, 2026-11-11) known limits: (1) source damage that stops `qpdf --check` (corrupt JPEG data) is refused at export, not at open: an intake `--check` would catch it but costs 3-20 s on large files; (2) files whose xref is broken *and* which are encrypted (even owner-only) are refused, because the pdf-lib repair cannot decrypt; (3) hybrid XFA+AcroForm forms are not offered for filling, although both assemble paths now drop the XFA part; enabling them needs a survey of the AcroForm side's scripts and appearances first; (4) MuPDF lays out text in widgets on rotated pages without /MK /R off the box (refused as "does not fit"); (5) no rendered before/after comparison inside the engine: ~0.1-0.5 s per typical file with MuPDF loaded, but 15+ s for one large map page, so it would need a time budget.
- Stamps known limits (survey 2026-11-11): a page whose content stream is corrupt (undecodable Flate) or ends inside a string, array, dictionary or inline image is refused as damaged, since anything appended would be swallowed; wrapping the original content in a Form XObject would isolate it but breaks tagged-PDF structure, so it is not done. Annotations paint above stamps: the export only warns when a visible annotation, push button or opaque field overlaps a stamp. A CropBox that misses the MediaBox follows PDF.js (MediaBox shown); poppler and MuPDF show an empty page there.
- Survey crash fixes (2026-11-11) known limits: (redaction on a very large map page is now refused up front, see the next bullet); a page whose dictionary itself has a qpdf warning (such as a name with a stray "#") is refused at open, because listing pages accepts only a clean qpdf run; opened copies are written without object streams (qpdf's JSON updates lose objects inside them), so a file that relied on them takes more memory while open and an export without compression comes out larger than the original.
- Redaction known limits (survey round 2, 2026-11-11): a page with more than 16 MB of drawing instructions (page content plus its forms and patterns) is refused up front ("too detailed to redact on this device"): the stage needs about 3 s and 40 MB per MB in Node (the 71-79 MB USGS map sheets: 3 GB, 3-4 min); not measured in a browser, where the limit may need to be lower. Letters, drawings, gradients and annotations touching a box still go whole (the export now says so for each kind); big text just below a box can still lose letters whose core (0.5 em above the baseline) reaches the box while their ink does not: keeping them would need the PDF.js check to know glyph ink. Every ActualText on a redacted page is dropped, so copying or searching complex scripts (Bengali, Urdu) elsewhere on that page gets worse. Each MuPDF rewrite moves text with horizontal scaling and TJ adjustments about 0.3 pt; the page is rewritten once unless an image is under a box, and a move of half a point is refused.
- Form flattening forced by redaction loses things outside the box (forms.ts, not fixed; survey files ao245c, sf62, sf2823, td1on, need-appearances-utf8, field-types): unsigned signature fields' "SIGN" markers disappear, push buttons lose their background, and NeedAppearances choice and list values (and some check styles) are not drawn. ## Stretch: make a flat form fillable (measured 2026-11-11: no-go as a general feature; tap to snap: no-go for recreating fields, meets a fill-in bar on held-out forms where the page shows the blank)

Detect blanks locally and deterministically: long underscore runs in text, drawn rules (filtered so table grids and underlines are not taken), small squares as checkboxes, with the nearest label as the field name. Offer them as suggestions the user confirms ("tap a blank to type", then "Make fillable" writes real AcroForm fields, verified like any export). No AI in the browser (no-network rule); AI naming or scanned forms with OCR would be a phase 3 opt-in server job. Rule: measure the detector on 10-20 real office forms first; if it is not near-perfect, pass on the feature.

### Measurement (2026-11-11, branch `forms-detect`, not wired into the app)

Detector: `src/lib/engine/forms-detect.ts` (MuPDF interprets the page contents only; pure geometry after that; median 13 ms, p95 ~55 ms, max 0.6 s per page in Node). Rules: underscore runs; open rules with a label left, above or below; table cells (empty cell, empty band under a label, space right of an item number); drawn squares, rings and hollow box glyphs (each glyph drawn once to a bitmap to check its shape); filled-frame boxes; comb rows; stacked lines; "office use" boxes suppressed. Harness: `npm run forms:measure -- sample|run|report|render` (`tools/forms-detect/`), output under `/home/garrett/pdf-survey/out-forms-detect/`.

Method. Truth = the visible, non-push-button widgets of survey files that have an AcroForm (text, checkbox, radio, choice, signature), first 6 pages. The flat version is the page contents without annotations, so widget appearances never reach the detector. Excluded before sampling: 77 XFA-only, 41 needing a password or with unreadable encryption, 27 damaged, 71 with no fillable field; owner-only encrypted files (permissions only, content readable) were kept, as were XFA+AcroForm hybrids. Samples are stratified round-robin by source (at most 45 per source, 15 per PDF-library test suite) and by producer inside each source. Rules were tuned on sample A (406 forms; 316 real-world files measured, 1035 pages); the numbers below come from a disjoint held-out sample B (274 forms; 212 real-world files measured, 698 pages; smaller sources were used up by A, so B leans to IRS, USCIS, GSA, US Courts and LiveCycle Designer files). A suggestion is right when it matches one widget of the right class and its rectangle is good: text-like, x IoU ≥ 0.75, y IoU ≥ 0.4 and bottoms within max(4 pt, 40% of the height); check-like, centres within a quarter side and size ratio 0.6–1.67, or the printed box lies inside a larger widget. A second suggestion on one widget counts as a false positive. File outcome: "all right" = no miss, no bad rectangle, no false positive; "mostly right" = at most max(2, 5% of the widgets) such errors.

Results, real-world forms, held-out sample B (tuning sample A in brackets):

| | text-like widgets | check-like widgets |
|---|---:|---:|
| widgets | 24,234 [23,736] | 5,079 [6,908] |
| no visible blank on the page (the widget draws its own box) | 8% [14%] | 5% [19%] |
| recall with a good rectangle | 60% [60%] | 81% [75%] |
| precision, all confidences | 80% [76%] | 92% [90%] |
| precision / recall at confidence ≥ 0.9 | 94% / 17% [93% / 19%] | 95% / 77% [94% / 67%] |
| precision / recall at confidence ≥ 0.95 (drawn squares only) | – | 97% / 66% [94% / 57%] |

Per file (B): all right 1.4%, mostly right 11%, a mess 88% (counting misses only where the page shows a cue: 4% / 16% / 81%). At confidence ≥ 0.95, 87 of 110 files with any suggestion had none wrong. No cutoff reaches 98%: the best rule, drawn squares, is 96.7% on B (98% on IRS and US Courts files, 81% on one EU form whose squares are text fields). Non-form documents (A: 200 files, 449 pages; B: 107 files, 238 pages): 3.7–5.3 suggestions per page and 30–37% of pages with one at any confidence; at ≥ 0.9, 0.5 per page on 8–10% of pages; at ≥ 0.95, 0.1–0.4 per page on 2–3% of pages.

Failure groups (by eye: 21 failing form pages from A and B and 4 non-form pages; a page can show several): no visible blank, the widget draws its own box or line (8 pages; 4,278 missed widgets in A, 2,126 in B); author granularity: stacked lines as one multi-line field or one per line, comb boxes as one field or one per box, Yes/No cells as checkboxes or text (7 pages; comb suggestions are 32–47% right); text or lines that are not blanks: section headings on rules, header and footer rules, label cells in tables, padding under questions, office-use and stamp boxes (9 pages; 6–12% of text suggestions); rectangle disagreements: one-line suggestion for a tall box, a widget that includes its label, a hit area larger than the drawn box (5 pages; 6–8% of text suggestions); wrong type by author choice: squares used for numbers, cells used as checkboxes (2 pages); drawing the detector does not read: very light grey ruled lines (1 page; dashed lines, hint letters in boxes and filled-frame boxes were fixed along the way); on non-forms, empty or padded cells in data tables (3 pages), and one filled-in flat 1040 that is really a form.

Verdict: no-go for "suggest every blank". Recall on cued text widgets is about 66% and only 1–2% of form files come out entirely right, far from near-perfect. The only narrow scope that comes close is checkboxes drawn as squares (confidence 0.95): about 97% precise with two thirds of checkboxes found on the held-out set, still below a 98% bar and still 0.1–0.4 bogus boxes per page on ordinary documents. Not verified: speed and memory in a browser (measured in Node only); forms outside the survey's government-heavy pile (few office or business forms from Word or LibreOffice); whether users accept a rectangle that differs from the author's widget (the rectangle rules above stand in for that).

### Tap to snap (2026-11-11, branch `forms-snap`, not wired into the app)

Idea: the user points, the tool only snaps. With the Text tool the user taps roughly where they want to write; `snapAt` (`src/lib/engine/forms-snap.ts`) returns the field rectangle near the tap that the ink suggests (a line to sit on, an empty cell, a square to tick, a comb row) or "no snap" (the app would place its plain box, as today). Candidates are the detector's raw output at any confidence (no stacking, no office-use filter, near-copies only removed; small cells count as checkboxes only when nearly square); the tap picks the nearest candidate within 8 pt (7 pt for squares), the smaller one on a tie, with a penalty for a candidate across a drawn rule. Confidence is "is this the right rectangle", calibrated per rule on sample A, lowered when another candidate is about as near, when the tap is 3 pt or more outside, across a rule, on a word, or beside a number in a data cell. Speed in Node: collecting the ink 12 ms median (p95 59 ms) per page as before, preparing 0.7 ms median (p95 4.6 ms), a tap 0.04 ms at p95 (max 4 ms). `similarTo` proposes the other candidates with the same rule and similar geometry ("more like this"). Harness: `npm run forms:snap -- ink|run|render` (`tools/forms-snap/`), same samples as above, output under `/home/garrett/pdf-survey/out-forms-snap/` (B in `holdout/`).

Method. Taps on every true widget of the measured pages: centre; sloppy (5 seeded points: text-like in the left third of the box at any height, check-like anywhere in the box grown by 3 pt); near-miss (3 points 0.5–6 pt outside, on the side of the nearest label word; widgets with no word beside them get none). A sloppy or near tap that lands inside another widget is dropped (B: 1,461 of 226k). Outcome per tap, with the rectangle rules of the detector's measurement unchanged (`tools/forms-detect/match.ts`): GOOD, NO-SNAP (harmless), BAD-RECT (found on the tapped widget, rectangle or class not acceptable), WRONG-TARGET (anything else). One addition: a comb row snapped over an author's one-widget-per-box comb counts as GOOD (a comb field puts one character per box); the strict count differs by at most 0.2 points. Harm: taps on paragraph words, empty margins and words in ruled table cells of non-form pages, and on form pages points at least 15 pt from any widget. Tuning on A only; snap rules were frozen before B was run.

Failure groups. By geometry, all failing sloppy taps on B (14,234): the snapped rectangle is wider than the widget, the author's widget being part of the drawn space (38%: a field inset in its cell, two widgets on one line or in one box such as EIN prefix and suffix or name parts, an unruled table body with invisible rows); height or bottom differ (23%: one-line widget at the bottom of a tall box, widget that includes its label, multi-line widget over stacked lines or the reverse); a checkbox widget in an empty cell or on a short line, snapped as text (24% with the reverse cases: Yes/No answer columns, "place an X" grids; the author's type choice); a neighbouring box or cell taken (8%: checkboxes 2–4 pt apart, where a tap 3 pt outside is nearer the next box); the snapped rectangle narrower (6%). Verdict, against the bar (on B, cued widgets, sloppy taps: at least 95% GOOD or NO-SNAP, at least 85% GOOD, BAD + WRONG at most 3%; rare snaps on non-blanks): no-go for tap to snap in general. Text fields fall short at every cutoff: 88% GOOD but 7.8% BAD + WRONG at all confidences, 53% GOOD at the cutoff that brings the errors under 2%. The errors are mostly the author's choice of rectangle, type or split, which the page does not show, so better geometry will not close the gap. Checkboxes in general fall short too (81.6% GOOD at A's cutoff), because many are empty table cells or short lines that the author made checkboxes. Go only for a narrower scope: snapping to drawn checkboxes (squares, rings, hollow box glyphs) when the tap is on or beside one, with ambiguous taps between two equally near boxes left unsnapped: 93% GOOD, 2.1% BAD + WRONG on B (88% / 0.8% on A), and essentially no snaps elsewhere. On USCIS forms the whole thing is near the bar (97.4% GOOD, 1.3% BAD + WRONG), so the gap is in other authors' habits, not in reading the page. "More like this" is precise (about 95%) but finds half to two thirds of the rest of a page, so it is a helper, not a form maker. Not verified: speed and memory in a browser (Node only); real people's taps (the tap models are guesses, the near-miss model especially); whether users accept a rectangle that differs from the author's widget; forms outside the government-heavy pile; the "drawn checkbox" population is found from raw ink by a simple size rule of my own, and the ambiguity cutoff was chosen after seeing B.

#### Tap to snap judged as fill-in (re-scored 2026-11-11, same taps, no new rules)

A different question: would a person filling in the form be happy with where their typing or tick lands? The app would not create a field, it places ordinary text or a tick. Rules (`tools/forms-snap/fill.ts`; every tolerance is a guess at what a person accepts, nothing here is measured on people):

- Placement from a text snap: baseline 2 pt above the snapped blank's bottom; text starts at the tap's x clamped into the snap (2 pt from either side). Starting always at the left edge was also scored and loses (sloppy, B [A]: 94.7% [87.6%] FILL-GOOD against 88.9% [79.7%]), because a line or cell often holds more than one blank.
- Placement from a check snap: a tick whose box is the snapped square.
- Plain placement as today (`PageEditor.svelte`, `textOrigin`): 11 pt text with its first line box (1.2 em) centred on the tap, starting at the tap, so the baseline is 4.3 pt below the tap; the Check tool's tick is a square of 0.026 × the page's shorter side (15.9 pt on Letter) centred on the tap.
- FILL-GOOD, text-like widget: the snap covers the widget (overlap at least half of the smaller area), the start x is inside the widget, and the baseline is within max(3 pt, 30% of the widget height) of the widget's bottom minus 2 pt; for a tall widget (≥ 26.4 pt, two lines of 11 pt) any baseline from 8 pt below its top to 3 pt below its bottom. Check-like: the tick's centre inside the widget or its printed box, tick size 0.5–1.5 × the printed box (else the widget's shorter side). A tick on a drawn square the author made a text field, or text that passes the text rule on a checkbox widget, is FILL-GOOD-OTHER-TYPE. Otherwise FILL-BAD if the snap covers the widget, WRONG-TARGET if not. "Worse than plain": a snap that is FILL-BAD or WRONG where plain placement at the tap would have been FILL-GOOD (a tap with no snap gets plain placement, so it is never worse).

Cutoffs: "old" are the rectangle-standard cutoffs fixed on A above; "new" are chosen on A under this standard (most FILL-GOOD with FILL-BAD + WRONG ≤ 3% and worse-than-plain ≤ 1%) and applied to B unchanged. #### Snap on tap (built 2026-11-11, branch `snap-tap`)

What ships: on a flat form, a Text tap on or beside a drawn blank puts the text in it, and a Check tap on or beside a drawn checkbox ticks the box; everything else places exactly as before. No field is created, nothing is shown before the tap, and the result is an ordinary stamp (moves, resizes and undoes like any other; it is never snapped again; its stored position is what the export draws, checked by an export round trip in `tests/engine/snap-tap.test.ts`). No "make fillable", "more like this" or Tab to the next blank.

- Where: `Engine.pageBlanks(source, pageIndex)` (contract added to `core/types.ts` with `PageBlanks`; `engine/snap-tap.ts`) reads the page in the engine worker with MuPDF (`collectInk`, `prepareSnap`) when Text or Check is armed on the page, once per page (the editor keeps 24 pages, `editor/snap-cache.ts`). The decision is `editor/snap.ts` (`textAt`, `tickAt`), loaded with the first request (about 4 KB with `snapAt`). A tap before the answer arrives places plainly; so does a keyboard placement.
- Pages: only PDF pages shown upright (no user rotation), with no fillable form widget on the page and the form's fields already read. Declined, with no snapping: scans and pages over the detector's path budget (a quarter-page image, 60,000 paths), pages over 4 MB of drawing instructions (checked before reading), reading over 2 s, a MuPDF page size that differs from the source's by more than 1 pt, any read error.
- Text gates: `snapAt` with all rules; the snap must be a text blank with confidence ≥ 0.42 (the fill-in cutoff chosen on A) and the spot where the text lands must show a visible cue by the measurement's cue notion (`engine/forms-cue.ts`, moved unchanged from `tools/forms-detect/cue.ts`: a line along the top or bottom of the text's line box, a box about its size, underscores). Placement: baseline 2 pt above the blank's bottom, start at the tap's x clamped 2 pt inside it; in a blank at least two lines tall (26.4 pt) the text keeps the tapped line, clamped inside the blank (chosen on A: of the gates tried, this was the one that cut cue-less harm without costing cued taps). A box under 10.4 pt tall steps the size down so capitals fit, never below 8 pt.
- Check gates: drawn checkboxes only (squares, rings, hollow box glyphs), confidence ≥ 0.6 (a tap about equally near two stacked boxes stays where it was tapped; that cutoff was picked after seeing B, see above); the tick takes the box's centre and shorter side. Cross and Dot are not snapped.
