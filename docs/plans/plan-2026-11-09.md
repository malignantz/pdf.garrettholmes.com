# Plan — 2026-11-09

## Vision

One workspace, no uploads, verified output.

A free PDF tool for people without an Acrobat license. Drop in any mix of PDFs
and images; every page appears in one grid. Arrange, rotate, delete, sign and
type on pages, then export once. Files never leave the device, and the site
refuses to hand over an output it could not verify.

The gap this fills: existing tools (iLovePDF, Smallpdf, BentoPDF, Stirling-PDF)
are one tool per page, so a merge-reorder-sign job means three round trips.
Research: `docs/research/2026-11-09-summary.md`.

## Principles

1. **Avoid, don't fail.** A feature ships only if it is near-100% reliable. Anything
   lossy or heuristic (PDF to Word, text editing, PDF/A) is out. Client OCR is out
   except one narrow, owner-approved case (2026-11-12): an invisible text layer on
   scanned pages of typed English, desktop only, declining rather than guessing, with
   the page picture never changed ("OCR in the browser (built 2026-11-12)" below).
2. **Verified output.** Every export passes `qpdf --check`, a page-count and
   page-size comparison against the plan, and a re-open in PDF.js before the
   download button appears. A failure shows what failed; no file is offered.
3. **Local, provably.** Phase 1 makes no network request after load. A
   Content-Security-Policy with `connect-src 'self'` enforces it. No analytics
   script, no third-party fonts, no CDN.
4. **Non-destructive.** The user's edits are a list of page references and
   stamps (`ExportPlan`). Originals are never modified; undo is free.
5. **Phone is a first-class layout,** not a shrunken desktop.
6. **Fast.** Static site. The shell loads without any PDF engine; engines load
   on first file. Budget: under 150 KB of JS before the first file is opened.

## Phases

| Phase | Scope |
|---|---|
| 1 | Merge, reorder, rotate, delete, duplicate, insert blank or other pages, extract/split, images to PDF, add or remove a known password, lossless compress, strip metadata, sign and type-on-page (signature, initials, text, date, check/cross marks), installable PWA, offline |
| 2 | True redaction with verification (MuPDF, lazy-loaded), real AcroForm fields, compress to a target size, page numbers and Bates stamps, highlight |
| 3 | Opt-in server jobs on a separate origin: OCR, Office to PDF |
| Never | PDF to Word, text editing, certificate signatures, send-for-signature, PDF/A, XFA forms |

## Architecture

SvelteKit 3 + Svelte 5 runes + TypeScript, `adapter-static`, SPA (`ssr = false`),
deployed as a Cloudflare Worker with static assets (`wrangler.jsonc`). Contracts live in `src/lib/core/types.ts`.

```
files ──► Engine.openPdf / openImage ──► Source (normalized PDF bytes)
                                            │
            DocStore: Source[] + PageRef[] + Asset[] + undo history
                 │                          │
        Renderer (PDF.js)            Engine.exportPlan
        thumbnails, page view        qpdf assemble ► pdf-lib stamps ► qpdf finalize ► verify
```

- **Engine** (`src/lib/engine/`) runs in a Web Worker.
  - Intake: `qpdf` decrypts and rewrites every input, which also repairs damaged
    cross-reference tables. If qpdf reports errors the file is rejected as unreadable;
    warnings become `Source.notes`.
  - Assemble: one `qpdf --empty --pages … --` call builds the page order, with
    `--rotate` for user rotation.
  - Stamps: only when the plan has stamps, `@cantoo/pdf-lib` opens the assembled
    file and draws images, text (embedded, subset font) and vector marks, honoring
    page rotation and CropBox.
  - Print-size cap: with `compress` and `printCap` (the app's default), photos holding
    more than 300 ppi as drawn are brought down to 300 ppi; nothing else changes
    ("Print-size cap for pictures" below).
  - Finalize: with `compress`, lossless repacking (MuPDF cleanup when worth it, an
    exact per-stream pass with a lossless JPEG repack, qpdf object streams; never bigger than the same plan
    uncompressed: "Lossless compress, round 2" below), AES-256 encryption
    (`password`), and metadata removal.
  - Verify: see principle 2.
- **Renderer** (`src/lib/render/`) wraps PDF.js: worker-based, lazy, cancelable,
  bitmap cache with a memory cap, pixel cap for iOS (16.7 MP per canvas).
- **DocStore** (`src/lib/doc/`) is framework-free TypeScript: state, commands,
  undo/redo. Svelte components subscribe through a thin runes adapter.
- **Workspace** (`src/lib/workspace/`) is the page grid and its actions.
- **Editor** (`src/lib/editor/`) is the single-page view for placing stamps.
- **UI kit** (`src/lib/ui/`) holds tokens and shared components. See `DESIGN.md`.

## Phase 2 design (2026-11-10)

Contracts for all of this are in `src/lib/core/types.ts`. MuPDF.js (`mupdf`, AGPL)
is the second engine: loaded by dynamic `import()` in the engine worker only when
a plan needs it (form fields, redaction, target size). It is never in the entry bundle.

Export pipeline, in order. Stages in brackets run only when the plan asks for them:

```
qpdf assemble ► [forms: set values, flatten] ► [redact] ► [stamps + numbering]
            ► [shrink images ► ] qpdf finalize ► verify
```

| Feature | How | Check that must pass (else no file) | Left out on purpose |
|---|---|---|---|
| Highlight | `highlight` stamp drawn with Multiply blend by pdf-lib: a box (slightly rounded rectangle), or with `pen` (2026-11-10) a freehand stroke, `PenStroke` = points in stamp space plus a width as a fraction of page height, drawn as one stroked path with round caps and joins; `box` then covers the stroke and moves with its points; or with `rects` (2026-11-11) selected text, one rectangle per line, each drawn like a box, all in one nonzero fill (see "Text highlighter" below). The editor's Pen simplifies strokes (RDP) and stores nearly straight ones as a two-point line snapped to level/upright within 4° | usual checks; pen points and rects must lie inside `box`; never both | resizing a pen stroke or a text highlight |
| Page numbers, Bates | `ExportOptions.numbering`; text in the stamp font, 0.5 in from the edge, upright on rotated pages | `numbering`: each label is read back from its page | per-page overrides, custom fonts |
| Redaction | `redact` stamp; MuPDF redaction annotations applied (text glyphs, image pixels, line art, links and annotations under the box). Forms are flattened first and metadata is stripped | `redaction`: two engines (MuPDF, PDF.js) find no text under any box, the box renders solid black; checked right after the stage and again on the final file (own stamps over a box are allowed) | search-and-redact, whole-page raster fallback |
| Form filling | `Engine.formFields` lists text, checkbox, radio and choice fields; answers live per source in `FormValues`; MuPDF writes values and appearances; optional flatten | `forms`: every answer reads back from the final file (or, flattened, no fields remain and text answers are on the page) | XFA, signature fields, fields computed by form scripts (shown read-only), rich text, comb layout fidelity beyond MuPDF's |
| Target size | `ExportOptions.targetBytes`; ladder of image resolution caps and JPEG quality, stops at the first step that fits; only plain 8-bit grey/RGB images are re-encoded | `visual`: each page rendered before and after must match within a tolerance; `target-size` | re-encoding 1-bit scans, CMYK, masked or indexed images; font subsetting |

Rules that follow from "avoid, don't fail":

- A redaction box that cannot be verified refuses the export; there is no "cover only" fallback.
- If the size target cannot be reached, the smallest verified file is offered with the real size.
- A source page duplicated in the grid shares its form answers with its copies (answers belong to the source).
- Form answers in thumbnails and the page view are a PDF.js preview; the exported appearance is MuPDF's.

Streams and paths are as in the ownership table. Engine work is split by module
(`mupdf.ts` loader, `forms.ts`, `redact.ts`, `shrink.ts`, `numbering.ts`), each with
its own test file, so streams do not edit the same code.

## Text highlighter (2026-11-11, branch `hl-text`)

Garrett asked for "a select text highlighter tool where you just select pdf text to get it highlighted".

Design. The highlighter bar is **Text | Pen | Box**. Text is the default on a page with text, Pen on one without; a mode picked by hand lasts the visit, except that Text is never active on a page without text (Pen stands in, and the bar says once per visit "This page is a scan with no selectable text. Use Pen or Box."; Text is shown disabled there). In Text mode a drag that starts on or near a word (within half a line, at least 10 px, 20 px on touch) selects from that word to the word nearest the pointer in reading order, whole words, whole lines in between; the would-be highlight is drawn live and stored on release. A double tap or double click on a word highlights the word. Elsewhere a drag pans (zoomed) or turns the page (fit), as without a tool; a second finger is a pinch and drops the selection. The tool stays armed; Escape (or the tool again) puts it away. While the words of the first page are being read (MuPDF loads, about 3.6 MB Brotli, once) the bar shows "Reading the page's text…" after 300 ms, a drag on the page does nothing, and Pen and Box work as before. Keyboard: the modes are a radio group like Pen | Box; a keyboard way to choose arbitrary words is out of scope (Enter on the tool in Text mode places the Pen's level stroke, as before).

Contract changes (`core/types.ts`). `highlight` stamps get optional `rects?: StampBox[]` (stamp space, each inside `box`, `box` their bounds, never together with `pen`); old stamps are unchanged and valid. `Engine.pageText(source, pageIndex): Promise<PageText>` with `PageText { words: TextWord[]; skipped }` and `TextWord { text, box, line }`, boxes in source-displayed fractions like `FormWidget.box`. Consumers updated: export (`stamps.ts`: every rect a rounded box in one path, one `f`; each rect counts for the annotation-overlap warning), validation (`core.ts`, `doc/store.ts`; the store's patch now copies arrays as arrays), view (`StampShape`: one SVG path, pointers on the rectangles only, no resize handle; thumbnails), move/duplicate/copy-to-pages (`pen.ts reboxPatch` → `text-select.ts mapRects`), redaction overlays (use `box`, unchanged). Protocol: `pageText` sends a source's bytes to the worker once; later calls name the source by id and a worker that dropped the file answers `NEED_BYTES` and gets them again (`client.ts`, `protocol.ts`); the worker keeps two opened documents.

Text source, chosen by measurement: **MuPDF structured text** (`engine/page-text.ts`), read twice from the page's own display list (no annotations or widgets): nominal boxes (origin, advance, font ascent/descent) and `accurate-bboxes` (glyph ink, vertically); option `clip` drops text clipped away; hidden layers are not run; invisible OCR text is listed; right-to-left text comes in logical (reading) order. Each line is laid out in its own frame (along/across the writing direction), so pages with /Rotate, user rotation, upside-down and vertical runs are one case; runs more than 3° off the axes are not offered. Across a line: the font's ascent and descent, capped by the tallest ink that font has on the page plus 0.1 em, never short of the line's own ink plus 0.1 em, then kept off the ink of the lines beside it (cut halfway between). Along a line: each word's advance box plus 0.1 em, at most half the gap to the next word. Words: cut at spaces only where the letters on either side are apart (Word draws a space under ligatures), and where letters are more than 0.25 em apart. Lines with 20% or more control codes, U+FFFD or zero-width characters (fonts without a Unicode map) are not offered; a structured-text line whose baseline jumps by half an em is split. The editor turns the words with the page, hit-tests on the main thread (`editor/text-select.ts`) and merges a line's selected words into one rectangle, never across an unselected word, with extra pieces where a nearly level line would grow over 1.15 × its height.

PDF.js text content was the other candidate (already loaded for rendering): its items give only a run's width, so words inside a run are placed by character count. Measured on the same words (below): PDF.js-based boxes miss ink by more than 1 pt on 40–44% of words and flood a neighbour on 12–13%; MuPDF 0.0% and 0.0–0.4%.

Measurement (`npm run hltext:measure -- sample|run|report|render`, `tools/hl-text/`, output in `/home/garrett/pdf-survey/out-hl-text/`, held-out sample in `holdout/`). Two disjoint stratified samples of 150 text PDFs each from the survey pile (19 sources, at most 15 files a source and 6 a PDF-library test suite, round-robin over producer families), first 3 pages, 12 seeded random word ranges per page (30% one word, 40% 2–6, 30% 7–40). Truth: the page's display list run through a device that keeps only glyphs, sorted into the selected words' glyphs and all others by origin, drawn at 4 px/pt. A range **misses** when selected ink lies more than 1 pt outside every rectangle, and **floods** when other ink reaches more than 15% of the line height into a rectangle. Rules were tuned on sample A only; B was run once at the end.

| | A (tuning) | B (held out) |
|---|---:|---:|
| ranges with ink | 3,646 | 3,431 |

Word ends are advance boxes, so a word's edge sits a side bearing away from its ink (p50 0.5 pt); the 0.1 em margin covers that, hence no misses. Failures by eye (A: 30 ranges, B: 11): text drawn over text on purpose (one qpdf overlay test file: 19 of A's), map labels in scattered order (4), text painted over by later content and redrawn elsewhere (4), inline symbols and maths glyphs the file lists apart from their line (a rectangle covers a symbol inside the selected line; 5), a duplicate glyph (1). Engine bugs found and fixed on the way: junk-text lines (no Unicode map) gave slivers; Word's space-under-ligature split words; a right-to-left full stop and a display heading made words or lines span other text; rectangles merged across unselected words.

Not verified: real phones, Safari and Firefox (Chrome emulation only: desktop and Pixel 7 projects, touch through CDP); time and memory in a browser worker (Node only; a phone is perhaps 3–5× slower, so dense pages may take about a second the first time); ink of invisible OCR text (its geometry comes from the OCR engine's font size and cannot be checked against the scan here).

## Lossless compress, round 2 (2026-11-11, branch `compress-lossless`)

Research: `/home/garrett/pdf-survey/out-compress-research/notes.md`. The bug it found: qpdf's `--recompress-flate` decodes the PNG predictor of Flate images and writes them back without one, so the default "Compress" could make a file much bigger (an arXiv paper 4.57 → 6.57 MB; corpus `compress-predictor.pdf` 71 → 190 KB).

What ships (compressed exports only; "Compress" is the default). Finalize with `compress` is now:

```
[MuPDF cleanup, when worth it] ► stream pass ► qpdf object streams, level 9 ► smaller of that and the same plan uncompressed ► verify
```

- **Stream pass** (`engine/pack.ts`). qpdf writes every stream's raw bytes out (`--json-output --decode-level=none --json-stream-data=file`); per stream the pass keeps the smallest of: the stream as it is; its inflated bytes deflated again (same `/DecodeParms`); for 8-bit images, the pixels with a PNG predictor chosen per row (`pngPredict`, Predictor 15), and, for images that had a predictor, the plain pixels. Every candidate is deflated in full with libdeflate level 6; the winners, biggest first, are deflated again at level 12 ("polish"). Before a candidate is used it is inflated again and must give back exactly its input, and a new predictor must un-predict to exactly the pixels; inflating is strict (one complete zlib stream with a matching Adler-32; trailing end-of-line bytes allowed). Left alone: XMP metadata, external (`/F`) streams, multi-filter and non-Flate streams (qpdf converts LZW and ASCII filters to Flate as before), damaged Flate data, and anything after the time budget. qpdf writes the chosen data back (`--update-from-json`, everything else byte for byte), then finalize packs object streams at `--compression-level=9`, without `--recompress-flate`.
- **MuPDF cleanup** (`engine/cleanup.ts`): `subsetFonts()` and `saveToBuffer('garbage=4,compress-fonts')` (drop unused objects, merge equal objects and equal streams; nothing else is recompressed). Fonts are not subset when the file has form fields, a widget or a free-text annotation (typing later uses `/DR` and `/DA` fonts), nor when MuPDF reports anything while subsetting (a damaged font, a content stream it cannot fully read: then it may not see every glyph; notes that a font was skipped or is not embedded do not count). The result is used only if it is smaller and keeps the structure: page count, each page's boxes, rotation, user unit, annotation count and resource names, the catalog's keys, the Info dictionary, the outline items, and every real number (MuPDF keeps reals as 32-bit floats and wrote `747.82195` as `747.82199`; a result with any number the input lacks is not used).
- **When MuPDF runs.** A qpdf-only estimate (`estimateCleanup`): saving ≈ 1.4 × bytes of duplicates (equal streams, and objects equal once what they point to is merged, a few rounds) + 0.7 × whole embedded fonts + 0.33 × subset-tagged fonts (fitted on the research sample with MuPDF run on every file). MuPDF runs when the estimate reaches 8 KB and 0.5% of the file if it is already loaded in the worker (forms, redaction, the highlighter load it), 32 KB and 1% if its wasm is in the service worker's cache, and 100 KB and 2% if it would be downloaded (about 3.6 MB Brotli, once; afterwards the cached rule applies). On the research sample these let MuPDF run on 77, 51 and 24 of 112 files and keep 99%, 93% and 82% of what running it everywhere saves. With a size target the cleanup runs once before shrinking; each shrink step gets the stream pass only.
- **libdeflate** (MIT): npm `libdeflate` 0.1.0 (2026-01-09, one release, one maintainer, a thin wrapper around Eric Biggers' libdeflate). Its 58 KB wasm is vendored as base64 (`engine/vendor/libdeflate/wasm.ts`, with the package's licence and the module's SHA-256, checked by a test) and instantiated by our own 100-line loader (`engine/libdeflate.ts`), not installed: the package declares Node ≥ 24 (CI runs Node 22 with `engine-strict`) and its Emscripten glue carries XHR, `fetch` and `require` paths. The module imports only memcpy and heap growth; output is byte-identical to the npm package's and every result is decoded again by us before use. Loaded by dynamic `import()` on the first compressed export, no fetch. If it fails to load, the platform's zlib (`CompressionStream`) is used.
- **Budgets** ("avoid, don't fail": what is left stays as it is): the fast pass stops 6 s plus 0.1 s per MB after the passes start (device clock); polishing takes at most 2 MB plus twice the file's size and 12 MB of data in all (a work budget, so the result does not depend on how busy the device is) and stops after 4 s; files over 256 MB skip both passes (memory: the passes hold the file about three times) and get object streams only.

Rules ("never bigger"):

- A compressed export is never larger than the same plan finalized without compression: both are built and the smaller is delivered (enforced). If the compressed file fails any verification check, the uncompressed one is verified and delivered instead; any error in the passes falls back to it as well. The app's verify step runs on whichever file is delivered.
- "Input" for a plain open → export with compress is the file the user opened; for a plan that merges, drops, rotates or stamps pages it is the same export without the new passes (today's compressed result). Neither can be enforced: the engine keeps only the opened (normalized) copy of a source, not the original bytes, and building today's result too would double the work. Both are measured below.
- Signed files: as for every export, the signature does not stay valid (intake says so); signature fields and values are kept like any other object.

### Lossless JPEG repack (2026-11-12, branch `jpeg-repack`)

Measurement behind it: `/home/garrett/pdf-survey/out-jpeg-repack/notes.md` (JPEG is 43–51% of the bytes of files with JPEGs; baseline Huffman optimisation is exact and saves about 6% of JPEG bytes).

What ships (compressed exports only, inside the stream pass, `engine/pack.ts` candidate J):

- Each DCT image XObject (`/DCTDecode` alone, or `[/FlateDecode /DCTDecode]` with no predictor) gets the same DCT coefficients with optimised Huffman tables, **baseline sequential, never progressive** (`engine/jpeg-repack.ts`). An already progressive input is transcoded to optimised baseline when that is smaller, else left (the measurement advises baseline: faster to decode, no old-printer or Acrobat risk). The dictionary is not changed; a Flate wrapper is kept and recompressed.
- Markers: the input's APP0 `JFIF`, APP2 `ICC_PROFILE` and APP14 `Adobe` segments are copied byte for byte in input order (libjpeg writes none of its own). EXIF, XMP, thumbnails, comments and other APPn are dropped: measured safe in MuPDF, PDF.js, poppler and Ghostscript; MuPDF ignores EXIF orientation in a PDF (checked); PDF.js in a browser zeroes EXIF before handing a JPEG to the platform decoder, but with two EXIF blocks it picks its own decoder instead, so such images are skipped.
- Skipped, left byte for byte ("avoid, don't fail"; reason in a debug note): signed files (the app's rule, PDF.js `/SigFlags` bit 1, widened to any `/Type /Sig` or `/ByteRange` dictionary); anything but one 8-bit Huffman frame SOF0/1/2 from SOI to EOI (12-bit, arithmetic, lossless, hierarchical, DNL, truncated, bytes before SOI); a libjpeg warning; a colour segment after the frame header; ASCII85, ASCIIHex, LZW or predictor wrappers; non-image DCT streams; inline images; output not smaller; any error or trap in the module; images whose coefficient buffers exceed 48 MB; images not started within the budget.
- Proof per image at export, before use: `jpeg.ts` checks the output's structure (baseline, same frame, component ids, sampling and table slots, the same colour segments byte for byte, nothing else); then `verifyJpeg` decodes input and output afresh and compares every DCT coefficient, the quantisation tables and the JFIF/Adobe flags (about 0.1 s/MB). The never-bigger rule and the final verify are unchanged.

## Saving progress (2026-11-12, branch `save-progress`)

Pick up where you left off: closing the tab no longer loses the open work. Code: `src/lib/session/` (`format.ts` record and strict reader, `storage.ts` IndexedDB, `owner.ts` which tab saves, `session.ts` controller, three components); `DocStore.restore`; intake's `onOpened`.

- **Where.** IndexedDB on this device only (database `pdf-workspace-session`): store `session` holds one small record (key `current`), store `blobs` holds `{ hash, size, blob }` keyed by SHA-256. Chosen over OPFS: the app already uses IndexedDB (saved signatures), one transaction can check the writer and the blobs and write the record together, and the blobs are written once and read once, which IndexedDB Blobs handle without a second storage system (OPFS would only pay off for in-place partial writes, which this does not need). Never localStorage for documents (it holds only the switch, `pdf-workspace.keep-work`). No network.
- **What is stored.** Each source's bytes once, written when the file is opened (blank pages and other sources on the first save): the engine's normalized bytes, so a restore needs no engine work. Saved signature/image assets the same way. The record: sources' facts (name, kind, page sizes, original size, notes, form flag, hash), pages in order with rotation and every stamp (text, signatures and images, check/cross/dot, highlights as box, pen and text, redaction boxes), form answers, whether the work had been exported, and the export options without file name or password. Not stored: undo history, selection, thumbnails (rendered again). A save writes only the record, debounced (0.4 s, at most 2 s), in one transaction that also checks every hash it names is stored.
- **Passwords.** Never stored, in any form. A file that needed a password is stored exactly as given (still encrypted) and, on Restore, the intake password dialog asks again (wrong password: asked again; Skip: its pages, answers and unused assets are left out and the rest restores). Owner-password-only files are stored as given too and reopen without asking. Decrypted bytes of a protected file are never written; its original bytes stay in memory while it is open, so turning the switch on later can still store it.
- **Restore** is never automatic: the start page shows "Pick up where you left off?" with "3 files, 12 pages, saved 2 hours ago" and Restore / Discard. All or nothing and verified: the schema number matches (an older or newer one is treated as damaged), every blob is present with its size and SHA-256, the record parses (strict per-kind stamp reader; `npm run check` fails if a stamp kind gains a key the reader does not copy) and `DocStore.restore` accepts it (page indexes, assets, highlight geometry, answers). Otherwise: "Your saved work could not be opened, so it was deleted." The restored document is the same `ExportPlan`, so it exports the same file (e2e: pixel compare of every page against an export made before the reload).
- **New work instead of answering.** The offer stays until it is answered or replaced; opening files replaces the saved session at the new work's first save (old blobs are swept then). A tab may only replace the exact record it was offered (writer and revision).
- **Expiry and deletion.** A saved session is deleted 7 days after its last saved change (checked on every load, device clock), on Discard, on Forget my work, when the switch is turned off, and on Start over once its undo window (9 s, the toast's 8 s plus a margin) has passed with the workspace still empty (at once if the tab closes first). Blobs no record or open source uses are swept after load and after saves that change the set.
- **Privacy controls.** A line above the pages: "Saved on this device only." or why not, with Settings ("Your work on this device", also in the More menu): the remembered switch "Keep my work on this device" (default on; off deletes what is stored now and is told to other tabs) and "Forget my work" (deletes the session and every stored file now; the open work stays open and is not saved again in this tab, new work is). Saved signatures are separate and unchanged. The privacy page says what is kept and when it goes.
- **Avoid, don't fail.** No IndexedDB or crypto, blocked storage, quota (`navigator.storage.estimate()` before files over 4 MB; write errors caught), a file over 1 GB, or a write failure: the app works as before with one line ("This work is not being saved. …") and the leave warning. The leave warning now appears only when work is unexported and not safely stored (a pending save, or any of the above).
- **Two tabs.** Web Locks (`pdf-workspace-session`): the first tab saves; a second works normally, says "This work is not being saved. The app is open in another tab." and takes over only if the first closes while it has nothing open. Fallback without Web Locks: a BroadcastChannel roll call; in any case every record write checks, in its transaction, that the stored record is this tab's own or the exact one it was offered, so no tab overwrites another's work.
- **App updates.** Restore reads stored bytes and the record only; the service worker's rule (auto-update only with no document open and one tab) is unchanged, and an update that reloads an empty tab loses nothing. A record from an incompatible build is declined by its schema number and deleted with the message above.
- **Not called:** `navigator.storage.persist()` (permission prompts). Safari (and iOS) may delete script-written storage after 7 days without a visit, private windows keep nothing, and any browser may evict it under storage pressure; the work is then simply not offered.
- **Cost** (desktop Chrome on the box, production build, a 52 MB 200-page file): storing the file at intake (SHA-256 + write) 0.67 s, in the background; saving one change 2–42 ms (median 7); the start page's check 5–28 ms after first paint (first contentful paint 76–204 ms with the saved session, 112–184 ms with none: no difference); Restore 0.43–0.56 s (read, hash, rebuild), all 200 tiles 0.8–0.9 s and the first thumbnail 1.3–1.5 s after the click. Not measured on real phones.
- **Contracts.** No change to `core/types.ts`. New: `DocStore.restore(snapshot, { clean })` and `DocSnapshot` (doc stream), `IntakeDeps.onOpened`, `App.onSourceReleased`, and the export options moved to a shared `workspace/export-form.svelte.ts`.

To keep work across a change, add a reader for the previous version that converts it to the current shape before `parseRecord`'s checks (records are small; blobs are raw file bytes and never need migrating), keep it for at least the 7-day expiry window after the release, then remove it.

## Print-size cap for pictures (built 2026-11-13, branch `print-cap`)

Garrett's idea: a PDF is for printing and reading, not for archiving photos. A photo or scan holding more pixels than a 300 ppi print of the size it is drawn at only costs file size. With Compress on (the default), such pictures are brought down to 300 ppi as drawn; everything else stays exactly as the lossless passes leave it.

What ships. An export option, **"Reduce oversized pictures"** (on by default, remembered with the other options; old saved sessions read it as on, no schema change), shown under Compress only when Compress (or Fit under a size) is on and the export has a picture that qualifies (`Engine.oversizedPictures`, asked once per source: qpdf lists the objects, MuPDF is loaded only if an 8-bit image of at least 0.5 MP exists; a picture page made by the app's own intake is answered from qpdf's listing alone). Hint: "3 pictures hold more detail than a printer can use. They are brought down to 300 dpi; text stays sharp." With it on, the Compress hint reads "Text and drawings stay exactly as they are." (off: "Lossless: images and text stay exactly as they are."). While exporting: "Reducing picture 3 of 20" and Cancel. After: "4 pictures reduced to 300 dpi, 3.2 MB saved." (nothing when none changed). The dialog's count is a hint; the engine decides (`ExportOptions.printCap` is sent whenever the option is on with compression). Code: `engine/print-cap.ts`, `workspace/print-cap-option.ts`, the dialog; the cap value is one constant (`CAP_PPI`; the dialog's copy `PRINT_CAP_PPI` is checked by a test).

Rules (`print-cap.ts`, reusing `shrink.ts`):

- Candidates are shrink's: plain 8-bit grey/RGB images whose every use was walked (masks, 1-bit, CMYK, indexed, `/Decode`, annotation, pattern, Type 3 and unfollowable-content images never are), at least 0.5 MP, **photo-like** (a JPEG source, or `isPhotoLike` on the samples: screenshots, logos and charts stay).
- **Threshold**: reduced only when 300 ppi as drawn keeps at most 80% of the pixels (about 335 ppi and up), each side capped by its largest drawn size.
- **Encoding**: MuPDF scales (a JPEG source is decoded from its compressed data into its own colour space, so samples are as the stream decodes them; others are read as stored), JPEG at quality 85 but never above the source's own (estimated from its luminance table), then transcoded to optimised **baseline** by the lossless repack's libjpeg (MuPDF writes progressive) and checked coefficient for coefficient.
- **Gain**: a reduced picture is used only if its stream is at most 80% of the original's stream as a compressed export delivers it (a JPEG original after the lossless repack).
- **Left alone**: digitally signed files (the repack's rule); JPEGs libjpeg finds corrupt (repack module, or one `qpdf --check` for images too big for it; MuPDF decodes such data silently, and re-encoding would turn a file today's export refuses into one it delivers); any image MuPDF reads with a warning; JPEG sources over 50 MP and other images over 25 MP (memory, below).
- Written back with qpdf `--update-from-json` (every other object byte for byte), then the usual finalize (stream pass, repack, object streams, never bigger than the same plan uncompressed). **Visual check** (`compareDocs`, 50 ppi blocks, shrink's limits) on every page showing a changed picture; a failing page gets its pictures back and is checked again; still failing: nothing changes. The stage never fails an export. The MuPDF cleanup's "already loaded" threshold looks at whether MuPDF was loaded before the cap ran, so a file the cap leaves alone is finalized exactly as without it.
- **Order**: where shrink runs (after OCR layers, forms, redaction, stamps). OCR reads the source pages and proves its layer on the pictures as they came, so it is unaffected; the final `text-layer` check reads the layer back over the capped picture. With redaction, the redaction check is told images were re-encoded (as for shrink).
- **Size target**: if the lossless file fits, the cap still applies; otherwise the capped file is the mildest step (used if it fits), then the ladder from the original pixels; the capped file is the fallback when the ladder cannot help. `savedBytes` there is exact (target-path finalize with and without the cap); without a target it is the image streams' own saving (finalizing twice would double the work; reported/real on held-out touched files: median 1.00, max 1.5, the excess from Flate originals the stream pass also shrinks).

Contracts (additive): `ExportOptions.printCap?`, `ExportResult.printCap?: { images, savedBytes, ppi }`, `ExportProgress { stage: 'pictures', done, total }`, `Engine.oversizedPictures(source): number[][]` (per picture, the source pages it is drawn on); `ExportOptions.compress` comment updated. `EngineOptions.printCapRules` and the survey's `SURVEY_PRINT_CAP` / `SURVEY_PRINT_CAP_RULES` are for measuring only.

## Pictures and split export (built 2026-11-13, branch `pictures-split`)

The demand research (`/home/garrett/pdf-survey/out-demand/report.md`) named "PDF to JPG/PNG" and "split a PDF into several files" as the biggest gaps that can be done exactly in the browser. Both are choices in the Export dialog, not new tools.

What the user sees. A **Save as** choice at the top: **PDF** (default, as before), **JPG pictures**, **PNG pictures**. The file name's extension follows the choice (`.pdf`, `.zip`, or `.jpg`/`.png` for a single page) and a line under it says what the zip holds ("A zip of report-001.jpg to report-012.jpg, in page order."). With pictures, a **Quality** choice (Screen (150 dpi), the default; Print (300 dpi)); the PDF-only options (Optimize, oversized pictures, fit under a size, lock form answers, keep blanks editable, remove metadata, password, searchable) are hidden; page numbers stay. With PDF and more than one page, **Split into several files** with **How to split**: Every page on its own, Every N pages ("Pages per file"), At these pages ("New file starts at pages": "5, 12"), and One file per original file (only when the pages come from more than one opened file); a line says what it makes ("Makes 3 files in one zip: pages 1–2, pages 3–4, page 5.") or what to fix. Progress: "Saving picture 3 of 20" / "Making file 2 of 9" (the engine's own step under it), the determinate bar, the time-left line, and Cancel. The result: "12 pictures in one zip, 3.4 MB" or "3 files in one zip, 1.2 MB" plus one line per file, the checks, and Download / Save as / Share.

How (code: `workspace/multi-export.ts`, `split-plan.ts`, `pictures-plan.ts`, `zip.ts`; `render/pictures.ts`; `render/sizing.ts` `pictureSize`):

- **Pictures are drawn from the verified export, never from the workspace.** One ordinary `Engine.exportPlan` with the user's page numbers (and forms locked and metadata removed as redaction forces), without compression, password, size target, OCR, editable blanks or the print-size cap (`pictureExportOptions`); then PDF.js (the page view's engine, through `pdfjs-loader.ts`, not a second renderer) draws each page of those bytes on an opaque white canvas at exactly the asked resolution (letter at 150 dpi is 1275 × 1650) and the browser encodes it (JPEG quality 0.9; PNG lossless). Redactions are therefore the applied ones (the export refuses to deliver unless the redaction check passes), and stamps, form answers, numbers and rotation are what the PDF shows. The page view's cache and width buckets are not used.
- **Memory.** One page is pixels at a time; the canvas is released before the next page. Per picture at most 16.7 MP (iOS's canvas limit) and 8192 px a side: a larger page is drawn at the largest whole dpi that fits and the result says so ("Page 4 is very large, so it was saved at 290 dpi instead of 300…"; A3 at 300 dpi is 17.4 MP). Finished pictures wait as Blobs until the zip is made (Chrome keeps large Blobs outside the page's memory). **Before starting** the dialog estimates their size (JPG 0.35, PNG 1.2 bytes a pixel: the worst cases measured below) against a budget of an eighth of the device's memory (`navigator.deviceMemory`; 3 GB assumed for phones and 8 GB otherwise where the browser does not say), 256 MB to 1.5 GB, and if it does not fit says so and blocks Export: "260 pictures at this quality would need about 2.4 GB, more than this device can hold at once. Save up to 106 pages at a time or choose Screen quality." (PNG at 300 dpi on a desktop; a phone without a memory figure refuses 260 PNG pages at 150 dpi and allows 159) If the real pictures outgrow the budget while saving, it stops and saves nothing ("Stopped after 140 of 260 pictures: they need more memory than this device can hold at once. Nothing was saved. Save about 112 pages at a time.").
- **One page** downloads the picture itself; **several** are one zip of `name-001.jpg` … (three digits, more past 999 pages), in page order.
- **ZIP**: written in the repo (`zip.ts`, about 100 lines), store-only (PDF, JPEG and PNG are compressed already), CRC-32 in the local headers, UTF-8 names, no ZIP64 (65,535 entries, 4 GB; a split makes at most 1,000 files). The archive is a Blob of the entries' own Blobs and small headers, never one big copy. Tested against `unzip -t` and Python's `zipfile`. No dependency was added.
- **Split** builds one ordinary verified export per part with the user's options (Optimize, oversized pictures, a size target per file, OCR, metadata, forms, editable blanks, and the **password on every part**), one after another; the parts' bytes go in one zip `name-part-01.pdf` …. If any part fails, nothing is delivered and the message names it ("File 2 of 9 (pages 3–4) could not be made: … No files were saved."). - Cancel: always offered for pictures and split. Between pictures and between parts it stops at once; inside an engine call it asks the worker, which is replaced after 10 s if it cannot stop (as for OCR).
- Saved work: the form gains `output`, `pictureQuality`, `split`, `splitRule`, `splitEvery`, `splitAt`, remembered like the other options; old sessions read the defaults (PDF, not split) and unknown values are replaced by the default (`FORM_CHOICES`). Saving pictures does not count as having exported the work (leaving still warns); a split does.

Contracts (additive): `ExportProgress` gains `{ stage: 'picture' }` and `{ stage: 'part' }` (reported by the dialog, not the engine); `PageNumbering.total?`. The engine is otherwise unchanged.

## Stretch: make a flat form fillable (measured 2026-11-11: no-go as a general feature; tap to snap: no-go for recreating fields, meets a fill-in bar on held-out forms where the page shows the blank)

Detect blanks locally and deterministically: long underscore runs in text, drawn rules (filtered so table grids and underlines are not taken), small squares as checkboxes, with the nearest label as the field name. Offer them as suggestions the user confirms ("tap a blank to type", then "Make fillable" writes real AcroForm fields, verified like any export). No AI in the browser (no-network rule); AI naming or scanned forms with OCR would be a phase 3 opt-in server job. Rule: measure the detector on 10-20 real office forms first; if it is not near-perfect, pass on the feature.

### Measurement (2026-11-11, branch `forms-detect`, not wired into the app)

Detector: `src/lib/engine/forms-detect.ts` (MuPDF interprets the page contents only; pure geometry after that; median 13 ms, p95 ~55 ms, max 0.6 s per page in Node). Rules: underscore runs; open rules with a label left, above or below; table cells (empty cell, empty band under a label, space right of an item number); drawn squares, rings and hollow box glyphs (each glyph drawn once to a bitmap to check its shape); filled-frame boxes; comb rows; stacked lines; "office use" boxes suppressed. Harness: `npm run forms:measure -- sample|run|report|render` (`tools/forms-detect/`), output under `/home/garrett/pdf-survey/out-forms-detect/`.

Method. Truth = the visible, non-push-button widgets of survey files that have an AcroForm (text, checkbox, radio, choice, signature), first 6 pages. The flat version is the page contents without annotations, so widget appearances never reach the detector. Excluded before sampling: 77 XFA-only, 41 needing a password or with unreadable encryption, 27 damaged, 71 with no fillable field; owner-only encrypted files (permissions only, content readable) were kept, as were XFA+AcroForm hybrids. Samples are stratified round-robin by source (at most 45 per source, 15 per PDF-library test suite) and by producer inside each source. Rules were tuned on sample A (406 forms; 316 real-world files measured, 1035 pages); the numbers below come from a disjoint held-out sample B (274 forms; 212 real-world files measured, 698 pages; smaller sources were used up by A, so B leans to IRS, USCIS, GSA, US Courts and LiveCycle Designer files). A suggestion is right when it matches one widget of the right class and its rectangle is good: text-like, x IoU ≥ 0.75, y IoU ≥ 0.4 and bottoms within max(4 pt, 40% of the height); check-like, centres within a quarter side and size ratio 0.6–1.67, or the printed box lies inside a larger widget. A second suggestion on one widget counts as a false positive. File outcome: "all right" = no miss, no bad rectangle, no false positive; "mostly right" = at most max(2, 5% of the widgets) such errors.

Results, real-world forms, held-out sample B (tuning sample A in brackets):

| | text-like widgets | check-like widgets |
|---|---:|---:|
| widgets | 24,234 [23,736] | 5,079 [6,908] |
| no visible blank on the page (the widget draws its own box) | 8% [14%] | 5% [19%] |
| recall with a good rectangle | 60% [60%] | 81% [75%] |
| precision, all confidences | 80% [76%] | 92% [90%] |
| precision / recall at confidence ≥ 0.9 | 94% / 17% [93% / 19%] | 95% / 77% [94% / 67%] |
| precision / recall at confidence ≥ 0.95 (drawn squares only) | – | 97% / 66% [94% / 57%] |

Per file (B): all right 1.4%, mostly right 11%, a mess 88% (counting misses only where the page shows a cue: 4% / 16% / 81%). At confidence ≥ 0.95, 87 of 110 files with any suggestion had none wrong. No cutoff reaches 98%: the best rule, drawn squares, is 96.7% on B (98% on IRS and US Courts files, 81% on one EU form whose squares are text fields). Non-form documents (A: 200 files, 449 pages; B: 107 files, 238 pages): 3.7–5.3 suggestions per page and 30–37% of pages with one at any confidence; at ≥ 0.9, 0.5 per page on 8–10% of pages; at ≥ 0.95, 0.1–0.4 per page on 2–3% of pages.

Failure groups (by eye: 21 failing form pages from A and B and 4 non-form pages; a page can show several): no visible blank, the widget draws its own box or line (8 pages; 4,278 missed widgets in A, 2,126 in B); author granularity: stacked lines as one multi-line field or one per line, comb boxes as one field or one per box, Yes/No cells as checkboxes or text (7 pages; comb suggestions are 32–47% right); text or lines that are not blanks: section headings on rules, header and footer rules, label cells in tables, padding under questions, office-use and stamp boxes (9 pages; 6–12% of text suggestions); rectangle disagreements: one-line suggestion for a tall box, a widget that includes its label, a hit area larger than the drawn box (5 pages; 6–8% of text suggestions); wrong type by author choice: squares used for numbers, cells used as checkboxes (2 pages); drawing the detector does not read: very light grey ruled lines (1 page; dashed lines, hint letters in boxes and filled-frame boxes were fixed along the way); on non-forms, empty or padded cells in data tables (3 pages), and one filled-in flat 1040 that is really a form.

Verdict: no-go for "suggest every blank". Recall on cued text widgets is about 66% and only 1–2% of form files come out entirely right, far from near-perfect. The only narrow scope that comes close is checkboxes drawn as squares (confidence 0.95): about 97% precise with two thirds of checkboxes found on the held-out set, still below a 98% bar and still 0.1–0.4 bogus boxes per page on ordinary documents. Not verified: speed and memory in a browser (measured in Node only); forms outside the survey's government-heavy pile (few office or business forms from Word or LibreOffice); whether users accept a rectangle that differs from the author's widget (the rectangle rules above stand in for that).

### Tap to snap (2026-11-11, branch `forms-snap`, not wired into the app)

Idea: the user points, the tool only snaps. With the Text tool the user taps roughly where they want to write; `snapAt` (`src/lib/engine/forms-snap.ts`) returns the field rectangle near the tap that the ink suggests (a line to sit on, an empty cell, a square to tick, a comb row) or "no snap" (the app would place its plain box, as today). Candidates are the detector's raw output at any confidence (no stacking, no office-use filter, near-copies only removed; small cells count as checkboxes only when nearly square); the tap picks the nearest candidate within 8 pt (7 pt for squares), the smaller one on a tie, with a penalty for a candidate across a drawn rule. Confidence is "is this the right rectangle", calibrated per rule on sample A, lowered when another candidate is about as near, when the tap is 3 pt or more outside, across a rule, on a word, or beside a number in a data cell. Speed in Node: collecting the ink 12 ms median (p95 59 ms) per page as before, preparing 0.7 ms median (p95 4.6 ms), a tap 0.04 ms at p95 (max 4 ms). `similarTo` proposes the other candidates with the same rule and similar geometry ("more like this"). Harness: `npm run forms:snap -- ink|run|render` (`tools/forms-snap/`), same samples as above, output under `/home/garrett/pdf-survey/out-forms-snap/` (B in `holdout/`).

Method. Taps on every true widget of the measured pages: centre; sloppy (5 seeded points: text-like in the left third of the box at any height, check-like anywhere in the box grown by 3 pt); near-miss (3 points 0.5–6 pt outside, on the side of the nearest label word; widgets with no word beside them get none). A sloppy or near tap that lands inside another widget is dropped (B: 1,461 of 226k). Outcome per tap, with the rectangle rules of the detector's measurement unchanged (`tools/forms-detect/match.ts`): GOOD, NO-SNAP (harmless), BAD-RECT (found on the tapped widget, rectangle or class not acceptable), WRONG-TARGET (anything else). One addition: a comb row snapped over an author's one-widget-per-box comb counts as GOOD (a comb field puts one character per box); the strict count differs by at most 0.2 points. Harm: taps on paragraph words, empty margins and words in ruled table cells of non-form pages, and on form pages points at least 15 pt from any widget. Tuning on A only; snap rules were frozen before B was run.

Results, real-world forms, sloppy taps on widgets with a visible cue, all confidences, held-out B [tuning A]:

#### Tap to snap judged as fill-in (re-scored 2026-11-11, same taps, no new rules)

A different question: would a person filling in the form be happy with where their typing or tick lands? The app would not create a field, it places ordinary text or a tick. Rules (`tools/forms-snap/fill.ts`; every tolerance is a guess at what a person accepts, nothing here is measured on people):

- Placement from a text snap: baseline 2 pt above the snapped blank's bottom; text starts at the tap's x clamped into the snap (2 pt from either side). Starting always at the left edge was also scored and loses (sloppy, B [A]: 94.7% [87.6%] FILL-GOOD against 88.9% [79.7%]), because a line or cell often holds more than one blank.
- Placement from a check snap: a tick whose box is the snapped square.
- Plain placement as today (`PageEditor.svelte`, `textOrigin`): 11 pt text with its first line box (1.2 em) centred on the tap, starting at the tap, so the baseline is 4.3 pt below the tap; the Check tool's tick is a square of 0.026 × the page's shorter side (15.9 pt on Letter) centred on the tap.
- FILL-GOOD, text-like widget: the snap covers the widget (overlap at least half of the smaller area), the start x is inside the widget, and the baseline is within max(3 pt, 30% of the widget height) of the widget's bottom minus 2 pt; for a tall widget (≥ 26.4 pt, two lines of 11 pt) any baseline from 8 pt below its top to 3 pt below its bottom. Check-like: the tick's centre inside the widget or its printed box, tick size 0.5–1.5 × the printed box (else the widget's shorter side). A tick on a drawn square the author made a text field, or text that passes the text rule on a checkbox widget, is FILL-GOOD-OTHER-TYPE. Otherwise FILL-BAD if the snap covers the widget, WRONG-TARGET if not. "Worse than plain": a snap that is FILL-BAD or WRONG where plain placement at the tap would have been FILL-GOOD (a tap with no snap gets plain placement, so it is never worse).

#### Snap on tap (built 2026-11-11, branch `snap-tap`)

What ships: on a flat form, a Text tap on or beside a drawn blank puts the text in it, and a Check tap on or beside a drawn checkbox ticks the box; everything else places exactly as before. No field is created, nothing is shown before the tap, and the result is an ordinary stamp (moves, resizes and undoes like any other; it is never snapped again; its stored position is what the export draws, checked by an export round trip in `tests/engine/snap-tap.test.ts`). No "make fillable", "more like this" or Tab to the next blank.

- Where: `Engine.pageBlanks(source, pageIndex)` (contract added to `core/types.ts` with `PageBlanks`; `engine/snap-tap.ts`) reads the page in the engine worker with MuPDF (`collectInk`, `prepareSnap`) when Text or Check is armed on the page, once per page (the editor keeps 24 pages, `editor/snap-cache.ts`). The decision is `editor/snap.ts` (`textAt`, `tickAt`), loaded with the first request (about 4 KB with `snapAt`). A tap before the answer arrives places plainly; so does a keyboard placement.
- Pages: only PDF pages shown upright (no user rotation), with no fillable form widget on the page and the form's fields already read. Declined, with no snapping: scans and pages over the detector's path budget (a quarter-page image, 60,000 paths), pages over 4 MB of drawing instructions (checked before reading), reading over 2 s, a MuPDF page size that differs from the source's by more than 1 pt, any read error.
- Text gates: `snapAt` with all rules; the snap must be a text blank with confidence ≥ 0.42 (the fill-in cutoff chosen on A) and the spot where the text lands must show a visible cue by the measurement's cue notion (`engine/forms-cue.ts`, moved unchanged from `tools/forms-detect/cue.ts`: a line along the top or bottom of the text's line box, a box about its size, underscores). Placement: baseline 2 pt above the blank's bottom, start at the tap's x clamped 2 pt inside it; in a blank at least two lines tall (26.4 pt) the text keeps the tapped line, clamped inside the blank (chosen on A: of the gates tried, this was the one that cut cue-less harm without costing cued taps). A box under 10.4 pt tall steps the size down so capitals fit, never below 8 pt.
- Check gates: drawn checkboxes only (squares, rings, hollow box glyphs), confidence ≥ 0.6 (a tap about equally near two stacked boxes stays where it was tapped; that cutoff was picked after seeing B, see above); the tick takes the box's centre and shorter side. Cross and Dot are not snapped.

#### Filled blanks as form fields (built 2026-11-12, branch `fill-fields`)

Garrett's follow-up to snap on tap: at export, the blanks the user actually filled by snapping become real form fields, so the next person can change the answers. General "make this form fillable" stays out (measured above); only blanks the user filled are made, at the rectangle the snap already found.

What ships:

- **The link.** A snapped stamp remembers its blank: `blank?: StampBlank` (`{ kind: 'text' | 'check'; box: StampBox }`, stamp space) on text and mark stamps (`core/types.ts`). Set by the editor on a snap (`snap-cache.ts` `snappedText` / `snappedTick` return it). **Kept** while the text is edited or recoloured. **Dropped** (DocStore, `doc/store.ts`) when the stamp is moved, nudged, resized or kept inside the page (x, y, size; a mark's box or kind), when its text gets a line break and the blank is under two lines tall (26.4 pt), when its page is rotated (the stamp turns with the page, but a form field over the blank cannot be drawn turned), and on copies (duplicate stamp, copy to pages; a duplicated page keeps its stamps' links: the stamps did not move). Undo and redo bring it back with the rest of the document. Saved sessions keep it (`session/format.ts` schema 2; schema 1 records still read, drop that after 2026-11-26).
- **Export dialog.** "Keep filled blanks editable", off by default, shown only when the exported pages have a linked stamp with something typed (or a linked tick); hint "The 7 blanks you filled become form fields, so the next person can change them." Not available with Lock form answers ("Not available with Lock form answers.") or when redacting (flattening is forced). Result line: "7 blanks are now form fields." plus "2 stayed as plain text." when some fell back. `ExportOptions.blankFields`, `ExportResult.blankFields { fields, plain }`, check `'blank-fields'`.
- **Engine** (`engine/blank-fields.ts`, the stamp stage `stamps.ts`, `core.ts`). Each linked stamp becomes a widget (merged field and widget, `blank_p<output page>_<n>`, unique against the file's field names) instead of page content: a text field whose value is the typed text, or a checkbox (`/Yes`, ticked). The appearance stream holds exactly the stamp's own operators (same embedded Noto Sans subset, colour, baseline) in a form whose box is the widget's, so it renders as the stamp did; no border or background (`/BS /W 0`, no `/MK /BC /BG`); `/MK /R` is the page's rotation. `/DA` names standard Helvetica (ticks: ZapfDingbats) from `/AcroForm /DR` at the stamp's size and colour, for viewers that redraw after an edit (and MuPDF in our own forms stage). `/NeedAppearances` is never set. Rectangle: the blank, grown to the text's ascent and descent plus 1 pt, starting 2 pt before the text; several answers on one blank become side-by-side fields (each ends where the next starts); corners on whole quarter points, outward (exact in binary, so the appearance's own translation cancels exactly: without it MuPDF and poppler drew a word one pixel off at 100 dpi).
- **Stays a plain stamp** (drawn as before, counted in "stayed as plain text"): text with characters outside WinAnsi (a redrawing viewer, and our forms stage, could not show them; characters outside the stamp font still refuse the export as before); several lines in a one-line blank; a stamp no longer on its blank (1.5 pt); a text that runs into the next answer on the same blank, and a second tick on one box; every linked stamp of a file whose form asks viewers to redraw its fields (`/NeedAppearances` true after the forms stage) or is XFA; any field the proof rejects.
- **Proof** before the file goes on: the same plan is also stamped the ordinary way; every page with fields is rendered by MuPDF from both (widgets included, 2 px/pt) and must match (a pixel differs at > 48 on a channel; 4 or more such pixels in a field's area, or outside all fields, fail); MuPDF and PDF.js read every field back (name, type, value or state, rectangle, page; MuPDF extracts the text its appearance draws); the page's own content must have lost exactly the fields' characters (not drawn twice). Failing fields are drawn as plain stamps and the stage runs once more; if that fails too, every stamp is drawn. After finalize, `'blank-fields'` reads every field back again from the final file (MuPDF and PDF.js, with the password).
- **Files that already have a form**: the new fields join its `/AcroForm` (`/Fields` appended; `Helv` / `ZaDb` added to `/DR` only when free, else a fresh name such as `PgsHelv0`; existing `/DA`, `/DR` entries and fields untouched). Snap never runs on pages with widgets, so the fields land only on flat pages. Signed files: as every export, the signature does not stay valid. Merged sources, duplicated pages (independent widgets, names per output page), `/Rotate` pages and pages the plan turns are handled and proved by render comparison.
- **Reopening our export**: the file has real fields, so intake offers the form and the editor's form layer fills them (MuPDF redraws them in Helvetica from `/DA`); snapping is off on those pages (they have widgets).

## OCR in the browser: measurement (2026-11-12, branch `ocr-measure`, not wired into the app)

Question: can "Make this scan searchable" (OCR in a Web Worker, everything from our origin, an invisible text layer over the unchanged page image, declining rather than producing junk) run in the browser? Verdict: **no-go against the bars set for it**; recall, junk, speed and download pass for ordinary typed English, the bad-page and highlighter-box bars do not. Principle 1 ("client OCR is out") stands. Harness: `tools/ocr/` (its own `package.json`; `npm run ocr:setup`, then `ocr:measure`, `ocr:scans`, `ocr:grade`, `ocr:osd`, `ocr:gate`, `ocr:browser`, layer prototype in `tools/ocr/layer/`); output and full notes in `/home/garrett/pdf-survey/out-ocr/notes.md`.

Engine: tesseract.js 7.0.0 (Apache-2.0; Tesseract 5 in wasm), English `fast` model (tessdata_fast), LSTM core, automatic page segmentation, Tesseract's own deskew (`rotateAuto`, boxes turned back), Sauvola binarisation, page rendered at 300 dpi. Lazy download: core 0.8 MB + glue, API and worker 0.06 MB, English data 1.6 MB, about **2.8 MB brotli** (8.2 MB raw); orientation detection adds about 4.3 MB. Zero requests outside the origin in Chrome with all other origins blocked, under `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'` (options `workerPath`, `corePath`, `langPath`, `workerBlobURL: false`; the defaults fetch from jsDelivr). Chrome and Node give identical words. The float `best` model aborts in the relaxed-SIMD core; `best_int` and `best` are no more accurate than `fast` at 300 dpi and 1.4× / 2.8× slower. The wasm traps on about 1.2% of runs in long-lived workers (not reproducible on a fresh worker), so a feature would need MuPDF-style worker replacement. Other engines (Scribe.js, PaddleOCR or docTR on ONNX Runtime Web, TrOCR) are larger, line-level or not yet a better bet.

Method. (a) Synthetic scans with exact truth: born-digital survey pages (English, level, visible text; the highlighter's own words and ink boxes as truth) rendered at 150/200/300 dpi and degraded (clean; scan with 0–2° skew, blur, levels, noise, JPEG; bitonal; fax; phone with uneven light). Dev set to choose the setting (two rounds, 34 and 32 pages), held-out 354 pages from 201 files, run once. (b) Real scans that carry an old OCR layer: agreement with that layer, a proxy (60 dev, 114 held-out pages). (c) 50 real scans with no text, graded by eye: 30 random OCR words a page (junk) and text strips with every word counted (recall), ugly ones on purpose. Words compared case- and punctuation-free, paired by position; a page is bad under 85% exact recall; boxes scored with the highlighter's miss and flood rules.

Dev findings that set the pipeline: without deskew, skew of 1.5–2° drops whole lines (16% bad pages; deskew brings the same pages to 6%); Tesseract's default Otsu fails on uneven light (phone 74% recall, Sauvola 97.5%); enlarging 150/200 dpi images before OCR changes little, so render at 300.

By kind (typed, 200/300 dpi): forms 97.0% recall, letters 96.2%, multi-column 96.5%, tables 91.5% (12% junk: rules read as "|" glued to words), small print 73%; words under 7 pt 60–67%. 12 of the 354 pages are bad even on a clean render (inline maths, tables, letterheads), with confident OCR. Declining. A page gate on OCR signals (mean confidence, low-confidence share, common-English share, word shapes), tuned on the dev pools only: no threshold reaches ≤ 2% bad pages on dev; at ≤ 5% it is mean confidence ≥ 84 and common English words ≥ 8%. Held-out with it: scan 200/300 dpi accept 94% of pages, recall 97.5%, junk 1.9%, **3.0% bad among accepted**; bitonal 2.3–3.6%; 150 dpi 4.0%; phone 6.1%. On the graded real scans it accepts all ordinary typed pages and declines all handwriting, maps and sideways pages and 7 of 8 non-English pages, but passes 3 of 5 hard typed pages. Orientation detection (Tesseract OSD) is reliable (88 of 88 turned pages, both sideways real scans) and its script guess flags non-Latin pages. Dropping words under confidence 50 halves junk (3.0% → 1.5%) for 0.8 points of recall.

Speed (system Chrome headless, 4 cores, fast model, deskew, pages served locally): **4.7 s per page median at 300 dpi** (p90 6.4 s, max 6.9 s), first result 6.1 s cold plus the download; 2 workers double throughput (+150 MB), 4 workers triple it (+370 MB); about 200 MB per worker. Chrome's DevTools CPU throttle does not reach dedicated workers; under a 25% CPU quota (phone proxy, an upper bound) a page takes 41 s. Proposal if ever built: render at 300 dpi, 2 workers on desktop, page cap 20 (about a minute), phones off or about 3 pages.

Writing the layer (prototype, 22 real scans, `@cantoo/pdf-lib` only): a 572-byte glyphless Type0 font (Tesseract's `pdf.ttf`, Apache-2.0), text along each OCR baseline in render mode 3, stretched spaces, original content wrapped in q/Q. Page pixels identical in MuPDF, PDF.js and poppler on all pages; MuPDF returns the words in order (PDF.js too, but one word per line on skewed lines; `pdftotext` follows its own column order); MuPDF search 717 of 717 hits in place; about 6 KB a page. The highlighter offers 99.2% of the words with no ink missed, but **4.5% of words flood into the next line** (no ink to keep bands apart): a band rule for invisible text would be needed. Also needed: OSD before writing (sideways pages give junk), skipping pages with text or an old OCR layer, a q/Q balance check; signed files lose their signature as with every export.

Avoid list (survey): only 3.2% of sampled pages are image-only (4.4% of files); 527 inventoried picture pages already carry an OCR layer and 367 mix a scan with real text (both: refuse or skip); 31% of image-only pages are under 150 ppi (refuse under 200 ppi, known from the image size); rotated content by OSD, non-English by OSD script and the English share, handwriting by confidence; no signed file has image-only pages.

Against the bars (held-out): recall ≥ 95% and junk ≤ 3% on accepted typed pages: met (97.5% / 1.9% synthetic, 97.0% / 2.5% real). ≤ 2% bad accepted pages: **not met** (2.3–3.6%). Boxes ≥ 97% right: **not met** as written (94–95% at 1 pt, 98% at 2 pt raw; 95.5% through the layer and the highlighter). Desktop ≤ 5 s median: met (4.7 s). Download ≤ 20 MB: met (2.8 MB). Narrowest version that comes close: typed English scans with pictures of at least 200 ppi, desktop only, page cap 20, deskew + Sauvola + OSD (only 0° Latin pages) + the gate + dropping low-confidence words + worker replacement + a highlighter band fix; it would still leave about one accepted page in 30–40 with a poor layer (page pixels never change, so only search and copy suffer). Not verified: real phones, Safari and Firefox, languages other than English, real download and caching, a second held-out set for the gate.

## OCR in the browser (built 2026-11-12, branch `ocr-build`)

Garrett decided to ship the narrow version from the measurement above, knowing that about one accepted page in 30 gets a poor text layer: the page picture never changes, so a poor layer only spoils search and copy on that page.

What ships. An export option, **"Make scanned pages searchable"** (off by default, remembered like the other options), with the line "Reads typed English on scanned pages so you can search and copy the text. The pages look the same." It is offered only on a desktop (`(pointer: fine) and (hover: hover)` and no coarse pointer) and only when the export has a page that qualifies (`Engine.scannedPages`, asked once per source; qpdf lists each page's images and only a page with a big enough image is opened in MuPDF). More than 20 qualifying pages: "This file has 34 scanned pages. The first 20 will be made searchable." While exporting: "Reading page 3 of 12" and Cancel (cancel makes nothing; the engine stops its OCR workers and answers `cancelled`). After: "12 pages made searchable. 2 pages were left as they were because the text could not be read well enough." It combines with compress, fit under a size (the layer is text; shrinking changes pictures only, and the final check reads it back), page numbers and a password. Code: `src/lib/engine/ocr/` (`eligible.ts`, `tess.ts`, `gate.ts`, `layer.ts`, `stage.ts`, `browser.ts`), `workspace/ocr-option.ts`, the dialog.

Which pages are tried: a page of a PDF source with no text at all (no real text, no old OCR layer, no invisible or clip text), essentially one picture (an image or image mask covering at least 85% of the page; the best such picture at least 200 ppi along both sides as drawn), at most 25 MP rendered at 300 dpi and a picture of at most 36 MP, UserUnit 1, no redaction box on it. At most 20 output pages per export, in document order (a source page used twice is read once).

Pipeline per page (as measured): MuPDF renders the page as displayed at 300 dpi, grey, without annotations → orientation and script (Tesseract OSD, legacy core; only 0° and Latin go on) → Tesseract (LSTM core, tessdata_fast English, PSM 3, its own deskew, Sauvola binarisation) → the gate on every word OCR returned (mean confidence ≥ 84 and ≥ 8% of words among the 100 commonest English words; `tools/ocr/gate.ts`'s signals, checked against the harness by a test) → words under confidence 50 dropped. A page that fails any step is left exactly as it was. Workers: tesseract.js's worker script, driven by our own small client (`ocr/tess.ts`) so tesseract.js never builds a URL (its defaults point at jsDelivr); 2 readers on 4+ cores, 1 otherwise, and one orientation worker, all started from the engine worker; a worker that fails (a trap, a time-out of 120 s) is replaced and the page tried once more, then declined; readers are replaced every 10 pages.

The layer (engine, in the export, so "never ship an unverified export" covers it): Tesseract's 572-byte glyphless font (Type0, Identity-H, ToUnicode), render mode 3, one line per OCR line along its baseline turned back from Tesseract's deskew (lines within 0.2° written level), per-word horizontal scaling to the OCR box, a stretched space between words and after each line, the em box sized from the words that sit on the line (a box reaching more than 1.5× the line's median above it or 0.6× below does not count), words whose OCR boxes touch or overlap slightly narrowed at the facing ends to leave 0.05 em (PDF.js joins them otherwise); the original content wrapped by its own q/Q nesting (`content.ts`, as stamps do). Checks per page before use: MuPDF renders the page identically before and after; every written word is where it was written (MuPDF structured text); PDF.js reads back every written word. A failing page is written again without its layer (if that does not clear it, no layer at all). The final file gets a `text-layer` verify check (PDF.js, with the password if any).

Highlighter: glyphs drawn in render mode 3 whose "ink" MuPDF reports as their font box (a glyphless font) now count as having no ink (`page-text.ts`; found with a device pass, only on pages where such a box appears), and two line bands of which one has no ink are cut halfway through their overlap. Normal text: the highlighter's own held-out measurement is unchanged (A 0.8%, B 0.3% either; `/home/garrett/pdf-survey/out-ocr-build/hl-text/`).

Bundling: tesseract.js 7.0.0 and tesseract.js-core 7.0.0 (`.wasm.js` builds, the wasm inside: LSTM-only for reading, legacy for OSD; relaxed SIMD, SIMD or plain chosen with wasm-feature-detect's probes) as Vite `?url` assets; tessdata_fast `eng` and `osd` vendored gzipped in `src/lib/engine/vendor/tesseract/` (SHA-256 checked by a test) and unpacked with fflate. All of it lazy: imported by the engine worker only when an export asks for OCR, never in the entry bundle, listed in `lazy.json` (not precached; cached on first use, so OCR works offline afterwards: e2e). Served sizes: worker script 34 KB gzip; LSTM core 1.46 MB gzip; legacy core 1.77 MB gzip; English data 1.98 MB; OSD data 4.29 MB; loader 5 KB: **about 9.5 MB on first use** (gzip; the data files are served as they are). CSP unchanged (`script-src 'self' 'wasm-unsafe-eval'`, `worker-src 'self' blob:` already allow it); e2e with every other origin blocked: no request leaves the site.

Contracts (additive, `core/types.ts`): `ExportOptions.ocr?`, `ExportResult.ocr?: OcrReport { eligible, cap, searchable, declined }`, `ExportProgress`, `ExportControl { onProgress?, signal? }` as an optional 4th argument of `Engine.exportPlan`, `Engine.scannedPages(source)`, `EngineErrorCode 'cancelled'`, `VerifyCheck` name `'text-layer'`. ## Removing printing and copying limits (built 2026-11-13, branch `unlock`)

The app always opened files that are locked with only an owner password (they open for anyone, but set "no printing", "no copying" and so on) and dropped the lock quietly, with a note full of jargon. Garrett decided to offer it openly. Nothing new runs; the feature is the wording, the facts behind it, and the tests and measurement. It stays in the one workspace (no tool page).

What the user sees.
- At open, a note (toast) that names only the limits that were set: "This file had limits on printing and copying. Your export will not have them." (printing, copying, editing, filling in forms); encrypted without limits: "This file was locked, though it opens without a password. Your export will not be locked."; opened with a password and limited: "Opened with its password. The file also limited printing and copying; your export will not have those limits or a password unless you set one." The toast is fine at 360 px (four lines).
- Because a toast goes after 5 s, the Export form keeps a note where the old password note was: "A file you opened limited printing and copying. This export will not." (the "had a password" note now only for files that needed one).
- The result of a PDF or split export says "Printing and copying limits removed." (the union over the files the exported pages came from). The old warning "<name> had a password; the exported file has none." is no longer given for files that opened without a password.
- Start page: "Lock, unlock, convert: Add or remove a password. Unlock files that block printing or copying. Turn photos into a PDF."; the meta description and README say the same; the privacy page adds "Passwords are never guessed. A file that needs a password to open still needs that password here; the app never guesses or gets around one."

Rules (`engine/limits.ts`, `core.ts` openPdf).
- Never guess: the engine tries no password, then only what the user types (the open or the owner password; both work and both remove the limits).
- What was limited is read at open from `qpdf --show-encryption` (the file's /P flags as qpdf reads them for every revision): print = low or high resolution printing not allowed; copy = extract for any purpose; edit = modify other, page assembly or annotations; fill = modify forms. It goes on the additive `Source.limits?: SourceLimits` (with `password`: opened with one). Derived at every open, never stored: protected files are stored as given and opened again on restore, so old sessions get it too.
- The exported file never has the original's encryption: `Source.bytes` is decrypted at open, and the existing `encryption` check (qpdf `--is-encrypted`) refuses an export that is encrypted without a password. With an export password the app encrypts AES-256 with user = owner password and no restrictions, and the `encryption` check now also requires that it allows everything.
- Declined with their own message, code `unsupported`, before anything is decrypted: certificate security (/Adobe.PubSec): "This file is locked to a digital certificate, so it cannot be opened here."; other handlers (FileOpen, Adobe LiveCycle Rights Management / APS, anything qpdf calls an "unsupported encryption filter"): "This file is protected by a rights-management system, so it cannot be opened here."; an unknown revision: "This file is locked in a way this app does not support, so it cannot be opened here."; a damaged lock: "This file’s lock is damaged, so it cannot be opened here." When qpdf fails before reaching the lock (damaged file), the bytes are searched for those handler names first; otherwise an encrypted file that cannot be repaired gets "This file is damaged, and because it is also locked it cannot be repaired here." (was "damaged and could not be repaired reliably").
- Digitally signed files keep their existing signature note.

Session test: `limits` is not stored and comes back on restore. ## Accessibility tags kept in exports (built 2026-11-13, branch `tags`)

Every export of a tagged PDF used to lose its accessibility structure: the assemble step (`assemble.ts`) builds a new document (`qpdf --empty --pages`), or, for forms, reduces the source's catalog to pages, form, layers and page labels, so `/StructTreeRoot` (headings, reading order, tables, `/Alt` picture descriptions, `/ActualText`), `/MarkInfo`, `/Lang` and `/ViewerPreferences` were gone; pages kept `/StructParents` and their content kept MCIDs that pointed at nothing. Found by the unlock survey (17 tagged files whose text changed). Garrett: "let's get the accessibility features fixed."

What happens now (`engine/tags.ts`; `planTags` decides from the catalogs, `graftTags` copies, `verifyTags` proves; wired in `core.ts` right after assembling):

| Export | Tags | Result line |
|---|---|---|
| One tagged file, all its pages (rotated, stamped, numbered, filled, blanks kept editable, Optimize, size target, OCR, password, unlocked, a whole split part) | kept whole | none; under Details "Accessibility tags: passed. Accessibility tags kept: N structure elements, …" |
| Pages removed, reordered, a split part, blank pages added | kept, pruned to the kept pages | none |
| Several tagged files merged (interleaved, pruned) | kept, one root | none |
| Anything blacked out | not kept | "Accessibility tags (used by screen readers) were not kept because something was blacked out." |
| Lock form answers on a tagged form | not kept | "… because the form answers were locked." |
| Pages from a file without tags (or a picture), or two trees that map a role two ways or share an ID | not kept | "… because pages from another file were added." |
| A page used twice | not kept | "… because a page is used more than once." |
| The source's tree does not match its pages | not kept | "… because the original file’s tags do not match its pages." |
| More than 25,000 structure elements (or 500,000 objects) | not kept | "… because the file has too many of them to copy on this device." |
| A tree the copy cannot write exactly (an empty name, an annotation without its copy) | not kept | "… because they could not be copied exactly." |
| The export's own tags check failed (the export is built again without them) | not kept | "… because they did not pass their check." |
| Saving as pictures | – | no line |

Not kept means the file as exports were before (no tree, no /MarkInfo). Split: one line per reason, "File 2: …" when only some parts.

The copy. Each tagged source's tree is read from its opened bytes (qpdf JSON of every object, cached per source) and written into the assembled file as new objects with one `--update-from-json`: every reference to a page, annotation or form XObject becomes the reference to its copy, found by walking each source page next to its output page (`/Annots` by position, `/Resources /XObject` by name, recursively); attribute objects, ClassMap entries and streams in the tree (embedded files of `/AF`, up to 24 MB) are copied with them. The ParentTree is rebuilt flat from the entries whose owner (page, annotation, XObject) is in the export; the first source's `/StructParents` numbers stay, a later source's move past them (its pages, annotations and XObjects are updated). RoleMap, ClassMap, IDTree (sorted when merged), `/Namespaces`, `/MarkInfo`, `/Lang`, `/ViewerPreferences` come along; a merged file whose `/Lang` differs puts it on its top elements. Page `/Tabs` and annotation `/StructParent` travel with the pages.

Rules.
- Pruning (pages removed): an element whose content (marked content, annotations) all lies on removed pages goes, with its subtree; one without content stays where its parent stays; one whose content lies partly on removed pages stays but loses `/Alt`, `/ActualText`, `/E`, `/T` and its table `/Summary`, because they may describe the removed part (removing pages must not leave their text behind, as for the outline); `/Ref` to dropped elements and `/Pg` to removed pages go.
- Reordered pages keep the tree's order: it is the document's logical reading order, which page order does not change. A screen reader following the tags reads the file in its original order; one following pages reads the new order.
- A repeated page would share its MCIDs and ParentTree entry with its copy: the export goes without tags rather than tagging one copy.
- Pages from an untagged file would sit outside the tree, and readers that follow the tags skip them: the export goes without tags, so readers read every page.
- Added content is an artifact: stamps, signatures, ticks, highlights, page numbers and Bates numbers (`stamps.ts`) and the OCR text layer (`ocr/layer.ts`) are drawn inside `/Artifact BMC … EMC`, after closing any marked-content sequence the page leaves open (`marked.ts` counts them). Unmarked content would not break the tree, but checkers report it as untagged content and a reader may attribute it to the last open element; an artifact is valid PDF/UA and touches no MCID. Limit: typed answers and the OCR text are therefore not read by screen readers that follow tags; new fields from "Keep filled blanks editable" are not in the tree either.
- Redaction (security first): any redaction box in the export drops the whole tree (`redacted`); the redact stage already deleted `/StructTreeRoot` and still does. Marked-content properties were checked first: `redact.ts` already drops every string-valued property (ActualText, Alt, E, …; not Lang) of every BDC on a redacted page, inline and named (`/Properties`), so a `/Span <</ActualText (secret)>> BDC` around redacted glyphs did not leak before this branch; the corpus file `tags-secret.pdf` now has secrets in a struct element's /Alt, /ActualText, /E, /T, an inline BDC /ActualText and a named property, and the test searches the fully decompressed export for each in Latin-1, UTF-16BE/LE and hex. The finer rule (drop only elements under a box) is not built.
- MuPDF cleanup: two equal empty struct elements without `/Type` would be merged by MuPDF's deduplication into one element reached twice; `cleanup.ts` now counts such elements, so the cleanup is turned down instead (the tags check caught it on the survey first). MuPDF.js 1.28.6 has no structure-aware page rearranging: `rearrangePages` drops the tree; qpdf keeps it only in place and without pruning. Neither was usable for pruning or merging.

The check (`verifyTags`, a `'tags'` VerifyCheck on the final file, with its password). The tree is read back (qpdf JSON) into a canonical form: per element its role, every key with references replaced (elements by number, pages by output page number, annotations by page and position, other objects inlined, strings compared as text), and its kids as element numbers, (page, MCID), (XObject, MCID) and (page, annotation) pairs; plus RoleMap, ClassMap, IDTree, ParentTreeNextKey and the catalog's tag keys. It must equal the form computed from the sources' own trees with the same pruning (not from what was written), so element, `/Alt` and `/ActualText` counts and every (page, MCID) → element pair are the source's (tier 1) or the expected pruned ones. Then: every page's, annotation's and XObject's MCIDs and OBJRs resolve through the ParentTree to the element that holds them, and no ParentTree entry names an element for content it does not hold; every MCID the tree gives a page is in that page's content (or the XObject's), read with a small lexer (`marked.ts`: strings, dictionaries, inline images skipped); no element points at a page or annotation that is not in the file; no element is reached twice. The same check runs on each source when it is first read: a source with any problem (wrong or missing ParentTree entries, MCIDs claimed twice or missing from the content, OBJRs to annotations on no page, keys owned twice, unreadable content) exports without tags (`damaged`). A failing check on the export builds it again without tags (`check`); the alternative uncompressed result is tried first, as for the other checks.

Cost (Node on the box, survey below): the tags' own steps (source read once per source, copy, final check) take median 0.13 s, p90 0.5 s, worst 7.5 s; the whole export takes median 0.17 s longer than without tags, p90 1.0 s, worst 19 s (a 174-page file with 10,417 elements and very large ParentTree arrays: 8.7 → 27.8 s), because the lossless passes and the final check dump the tree too. Exports are 3% bigger at the median than today's (p90 19%: the tree itself) and never bigger than the file as given. Budget: at most 25,000 structure elements (about 0.6–2.4 ms each across the export: the tree is read, copied and checked as JSON, and every lossless pass dumps it again), so the worst case stays near a minute on the box; files with more elements, or more than 500,000 objects, export without tags (`large`).

Contracts (additive): `ExportResult.tags?: { kept: true } | { kept: false; reason: TagsDropReason }` (present when a source is tagged), `TagsDropReason`, VerifyCheck name `'tags'`; `EngineOptions.keepTags` (measurement only). No new Source field (the engine decides at export), so sessions are unchanged. UI: `workspace/logic.ts` `tagsLine`, `multi-export.ts` `splitNotes`, the dialog lists a passing 'tags' check only under Details.

## Marks turn with their page (2026-11-13)

Before this, rotating a page left every stamp at its place on the page *as displayed*, so a redaction or highlight placed first ended up over other content (for a redaction, a privacy failure). Now `DocStore.rotatePages` (grid Rotate, Rotate all, the editor's Rotate page, keyboard R; one undo step) turns every stamp with its page (`doc/turn.ts`, pure, per quarter turn clockwise):

- Boxes, text-highlight rectangles and pen points map (x, y) → (1 − y, x); a box takes its four corners. Fractions of the page height (text `size`, pen `width`) are divided by the page's width/height so the real size stays.
- Text, pictures and check marks are drawn upright, so they carry the additive field `turn?: 90 | 180 | 270` (clockwise from upright; absent = 0), in `core/types.ts` and the saved session (schema 3; schemas 1 and 2 still read, `turn` absent). Text: `x`, `y` stay the corner the first line starts at, the pivot of the turn. Picture and check: `box` is the turned stamp's bounding box on the page as displayed; the drawing is made upright in a box of swapped sides and turned into it (`geometry.ts` `contentTurnMatrix`, `pivotTurnMatrix`; CSS `turnerStyle` in the editor and thumbnails). Cross and dot look the same turned: only their box moves.
- Links to snapped blanks are still dropped on a rotation, and a turned stamp cannot be linked (a form field cannot be turned); four turns bring every other mark back to its start within floating-point rounding (1e-15).
- Editor: turned text can be selected, moved, copied and deleted but not edited or resized in place (it says so; delete it and type it again, or turn the page back). Pictures and checks resize as usual. A highlight's rounded corners are a share of the page height, so after a turn they differ by under a point; nothing else about a mark changes.
- Tests: `tests/doc/turn.test.ts` (per kind, four turns, undo/redo), `tests/engine/turn-export.test.ts` (redaction over known text at 90/180/270, rendered export compared with the upright export turned).

## Faster final check (2026-11-14, branch fast-check)

Garrett: the last step of a long export, `qpdf --check` on the finished file, was most of the wait (39–55 s of a 260-page scanned export). Goal: shorter, without weakening "never ship an unverified export". Tools: `tools/fast-check/` (`npm run fastcheck:measure`, `npm run fastcheck:browser`); results, measurements and report in `/home/garrett/pdf-survey/out-fast-check/` (`report.md`).

**Where the time went.** Generated files (`tools/fast-check/gen.ts`): `scan-260` (260 letter pages, each its own 1275 × 1650 grey-noise JPEG, 70.6 MB), `photo-260` (260 different 1600 × 1200 colour JPEGs, 32.8 MB), `text-1000`, `streams` (big DCT, Flate, JPX, CCITT and JBIG2 streams). On `scan-260`'s plain export (Node, box quiet) the check took 34 s; everything around it is small: a fresh qpdf instance 4–30 ms, copying the file into the wasm file system 44 ms, parsing 0.1 s, writing the whole file without decoding 0.3 s, `--is-encrypted` 0.15 s, the PDF.js re-open 0.1–0.2 s. The file is copied into qpdf once per verify step, but those steps are each well under a second. Not startup, not the copy, not the FS layer (MEMFS, read in whole blocks), not a second pass. A CPU profile of the check showed **two thirds of it in zlib deflate** (`deflate_slow`, `longest_match`, `compress_block`) and about a fifth decoding the JPEGs. The cause is in qpdf (`QPDFJob::doCheck`): it writes the file to a discarding pipeline with every stream it can decode decoded, and that writer keeps the default "compress streams" setting, so each decoded picture is deflated again at zlib's default level and then thrown away. Native qpdf does the same (same pinned sources built with gcc -O2: the check of `scan-30` 3.1 s CPU, decoding alone 0.66 s; the wasm 4.5 s and 1.27 s, so wasm is about 1.5–1.9× native). The npm build is `-Oz -flto` with JavaScript-based C++ exceptions; a rebuild with Emscripten 6.0.13, `-O2` and wasm exceptions made the full check 4% faster and the fast one 16%, for a wasm twice the size: not adopted (backlog).

What `qpdf --check` decodes, for the record (qpdf 12.2 source and the fault test below): content streams are parsed, so decoded; DCT, LZW, RunLength, ASCIIHex/85 and filter chains are decoded (and re-deflated); a stream whose only filter is FlateDecode is passed through raw (the writer does not recompress Flate), so damaged Flate data in a picture or a font is **not** caught by the check, today or now; JPX, JBIG2 and CCITT are never decoded.

**What changed.** `src/lib/engine/final-check.ts`: the export's structure check is the same `qpdf --check --show-npages` on the same bytes, in an instance where a prelude run (`--compression-level=0 --empty /dev/null`) first set qpdf's process-wide Flate level (`Pl_Flate::compression_level`, which `--check` itself does not take) to 0, "stored": the decoded pictures go to the discard pipeline uncompressed. `qpdf.ts` gains `QpdfRunOptions.prelude` (a command run first in the same instance; its output discarded; if it does not exit 0 the main command is not run). In `core.ts` only the call in `verify` changed (and a debug note `final-check: fast|full|full-after-fast, … ms`). `EngineOptions.fullCheck: true` forces the old check (additive; `src/lib/core/types.ts` unchanged). The progress of the check is real as before (bytes of the file qpdf has read, `readProgress` on the same instance); a full check after the fast one starts the bar again from 0.

**Why it is safe.** (1) Nothing that verifies anything changed: the same objects are parsed, the same streams decoded by the same code with the same filters and parameters, the same content streams parsed, the same warnings counted and printed; only the encoding of bytes nobody reads. Deflate at level 0 cannot fail or warn where level 6 would not (same zlib, same window). (2) The fast check can only accept: anything but a clean result (exit 0 and "No syntax or stream encoding errors found"), or a prelude that did not exit 0, runs the full check in a fresh instance, and that output is what the export uses (so the "damage the original already has" comparison sees exactly today's text). (3) Emscripten keeps the instance's statics between `callMain` calls (no `EXIT_RUNTIME`); a test proves the level carries over (a `--recompress-flate` write after the prelude comes out stored, a fresh instance at the default level). (4) Measured: no disagreement anywhere (below).

**Fault injection** (`tests/engine/fault-inject.ts`, `tests/engine/fast-check.test.ts`, self-generated from corpus exports, small): 56 kinds of damage (truncated file and stream, wrong /Length, corrupt Flate in content, image and font streams, corrupt bytes, markers, EOI and SOF in copied JPEGs, corrupt and inconsistent object streams and xref streams, broken xref entries, startxref and keyword, dangling references, wrong and damaged page tree, catalog and trailer damage, content syntax errors, object syntax damage, damaged /Encrypt entries and encrypted data, garbage and zeroed blocks) on 6 bases (photos plain, compressed, AES-256, JPEG kinds compressed, a stamped file, an uncompressed copy): 212 damaged files; the full check rejected 168, the fast check the same 168, with byte-identical exit code, stdout and stderr on all 212. Faults both pass (44) are ones qpdf does not look at (Flate damage in pictures and fonts, entropy-coded bytes that still decode, a page /Count qpdf recomputes, dangling image references read as null): unchanged, and kept in the test.

**Numbers.** Chrome on the box (system Chrome, engine in a dedicated worker, box quiet, two runs each), plain export (Optimize off): `scan-260` 34.2–34.8 s → **11.6–11.7 s** (its check 33.3–33.9 → 10.7–10.8 s); `photo-260` 40.3–40.7 → 16.5–16.7 s; `text-1000` 1.6 s both. Under load from other sessions (load 6–13) the same `scan-260` export was 46.7 → 12.8–15.1 s. Node, quiet: check of `scan-260` 34.0 → 11.5 s, `photo-260` 40.4 → 18.1 s. Survey (100 files of 2–45 MB, round-robin across 18 sources, median 7.9 MB; tuning half 55 by sha256, held-out 45; nothing was tuned, the level was chosen on the generated files), the check of each file, one worker, box quiet: median 0.58 → 0.50 s, p90 15.6 → 5.4 s, worst 29.0 → 18.7 s, total 387 → 188 s; held-out half median 0.90 → 0.72 s, p90 13.1 → 5.4 s, worst 29.0 → 18.7 s; no file more than 0.1 s slower. Export pairs on the survey (two workers, box loaded, so noisy): the plain export's check p90 31.9 → 11.7 s; files where the fast check looked slower were re-timed quietly and were 5–12% faster. Where the check is mostly content parsing (forms, maps, long text), the gain is small; where it is pictures, 2–3×.

**Agreement.** 776 check comparisons (corpus files and their exports, generated files, the 100 survey files, 300 more survey files of any size and state, damaged ones included): identical output on all 776, 288 rejected by both. 347 export pairs (plain and default exports, fast engine vs `fullCheck` engine): same outcome, checks and warnings on all 347 (6 refused by both). Default exports differed in size in 20 of 162 pairs: the Optimize stream pass works to time budgets and the box was loaded; the check runs after it and does not change the file. `npm test`: one unrelated shrink test hit its 120 s timeout while the survey ran on the box and passes alone. E2E `workspace-export.spec.ts` and `workspace-job.spec.ts`: 22 passed, 6 skipped.

**Not done.** The rest of the check is the real work (decoding every JPEG), so further speed would need: skipping JPEGs copied unchanged from a source that passed the same decode (the intake does not decode; that would move the cost to opening or to a background check), checking in parallel workers (qpdf has no way to check part of a file; per-page splits would check something other than the file delivered; each worker holds the file, a problem on phones), or the faster build above. The other `--check` runs (`checkStructure` for images and blank pages, the print-size cap's) still use the full check; they would gain the same way.
